# 实现与方案的差异

对照 `harness-技术方案.md`（下称「方案」），记录实现里与方案不一致、或方案没写而实现自定的地方。方案本身暂不改；实现有变化时同步更新本文件。

---

## 一、已定的设计改动

### 1. 命名：`包名_键名`

- **方案**：Operation 名为 `包名.函数名`，如 `fs.read`（1.3、6.1、7.3、附 A）。
- **实现**：`包名_键名`，如 `fs_read`。键名是它在插件对象 `operations` / `decorators` 里的键（见 12）。包名只含小写字母、数字与 `-`；键名只含字母与数字；整名最长 64。名字里恰好一个 `_`，就是分隔符。装上插件（`kernel.use`）时校验包名与整名。
- **原因**：模型的工具名只接受字母、数字、`_` 与 `-`。这样 Operation 名原样就是工具名，事件、模型历史、日志里处处同名，便于追踪，也不需要任何转写。
- **代码**：`stdlib/kernel/names.ts`、`kernel.ts`（use、register）。

### 2. Operation 的声明：`op()` / `decorator()`，入参用 Zod

- **方案**：导出函数即 Operation，JSDoc 正文是 `usage`，标签写 `@public`、`@decorators`、`@only` 等；d.ts 与 JSON Schema 由同一个工具在构建期从 TS 类型生成（6.1、7.3、R4、R19）。
- **实现**：插件对象的 `operations` / `decorators` 里放 `op({ input, usage, public, decorators, only, exclude, impl })` 或 `decorator({ onError, fn })` 的声明（插件对象见 12）。入参是 Zod schema：TS 类型由它推出，运行时按它校验，交给模型的 JSON Schema 在注册时由 `z.toJSONSchema` 生成。公开与 `api` 的 Operation 的 schema 须能转成 JSON Schema：不校验、只按类型交给实现的值（如 pi-ai 的 `Message`）写 `opaque<T>()`，JSON Schema 里是 `{}`；`z.custom` 转不成。
- **原因**：一处定义同时得到类型、schema 与校验；不需要构建步骤，也不用解析注释。
- **影响**：`usage` 从 JSDoc 挪到字段；script 包在 QuickJS 里带上 Zod，求值约 0.15 秒，每个进程一次（见 17）。
- **代码**：`stdlib/kernel/plugin.ts`、`kernel.ts`（use）。

### 3. 当前 Run 经显式的 `ctx` 传递

- **方案**：用 AsyncLocalStorage 绑定当前 Run，Operation 恰好一个入参；插件之间 `import { read } from "fs"`，打包时换成按名字的调用（6.2、3.1、R4）。
- **实现**：`ctx` 作为第一个参数：实现是 `impl(ctx, input)`，装饰器是 `fn(ctx, run, next)`。调别的 Operation 写 `ctx.ops.fs.read(input)`，名字是变量时写 `ctx.call(name, input)`（类型见 14），返回结果对象（`{ ok, value }` 或拒绝），而不是值本身。
- **原因**：没有隐式上下文，插件可以传假 `ctx` 单测，也没有「上下文丢失」这条残余风险（方案 10.8、附 C）。
- **代码**：`stdlib/kernel/run.ts`（Ctx）、`kernel.ts`（execute）。

### 4. 装饰器 id 不自定义

- **方案**：`@decorator <id>` 声明注册名（5.2）。
- **实现**：装饰器 id 与 Operation 同一套命名，就是 `包名_键名`。
- **代码**：`stdlib/kernel/kernel.ts`（use）。

### 5. 取消用 `ctx.signal`，不设 `run.cancelling` 责任链

- **方案**：取消「走 `run.cancelling` 后转 killed」，由插件在生命周期责任链上收尾（5.1、附 A）。
- **实现**：每个 Run 带一个 AbortController，`ctx.signal` 在 Run 被杀（取消或关停）时 abort。原语把它传给 fetch、子进程等，IO 当场中止。没有 `run.cancelling`。
- **原因**：比责任链简单，是 JS 的惯用法；内核不用等插件收尾，取消不会被拖慢。
- **代码**：`stdlib/kernel/kernel.ts`（kill）、`run.ts`（Ctx.signal）。

### 6. 装饰器的 `ctx` 上没有 `tools()`

- **方案**：调用方是装饰器时，交给模型的工具缺省为空（8.1）。
- **实现**：更严格：装饰器的 `ctx` 类型是 `Omit<Ctx, "tools">`，装饰器里写 `ctx.tools()` 直接编译不过。
- **代码**：`stdlib/kernel/chain.ts`（DecoratorCtx）。

### 7. 交给模型的工具由调用方显式传入

- **方案**：`model.complete` 的 `tools` 缺省为调用方能力面里公开的 Operation，不含 `model` 包自身（8.1）。
- **实现**：调用方用 `ctx.tools()` 取得工具列表，再作为入参传给 `model_complete`。`model_complete`、`model_compact` 公开（script 包 `agent` 要调），声明 `tool: false`，不出现在工具列表里：「不含 `model` 包自身」由 Operation 自己声明，内核不认包名。`time_now`、`kv_get`、`kv_set` 也是公开而 `tool: false`。
- **原因**：`model_complete` 保持为纯原语，工具列表只是数据；调用方传常量列表，前缀更好控制。`model` 是应用的插件，内核不该写死它的名字。
- **代码**：`stdlib/kernel/kernel.ts`（toolsIn）、`stdlib/plugins/model/index.ts`。

### 8. 放行不发事件

- **方案**：装饰器链每一环的处置都进事件流（3.7-4、9.1）。
- **实现**：链序记在 `run.started.chain` 里；放行不发事件，只有改写、拒绝、出错各发一条（`decorator.rewrote` / `decorator.rejected` / `decorator.failed`）。
- **原因**：少发大量「什么都没做」的事件；链序加上这三类事件，足以还原每一环做了什么。
- **代码**：`stdlib/kernel/chain.ts`。

### 9. `running` ↔ `waiting` 不发事件；能力面不写进事件

- **方案**：每个状态转换点都发事件（9.1）；复盘靠「Run 建立时的能力面」（9.6）。
- **实现**：父 Run 何时在等，可由子 Run 的 `run.started` / `run.exited` 推出，不单独发事件。能力面由 Operation 的声明静态决定，看 operation 名加产物版本即可还原，不在每个 `run.started` 里重复。

### 10. 内核不注册 Operation；park 的 Operation 在 stdlib 的 harness 插件里

- **方案**：`harness.park`、`harness.exec` 是内核提供的 Operation（3.5、附 A「`harness` 包」）；`harness.park` 是唯一不靠子 Run 而进入 `waiting` 的 Run（3.4）。
- **实现**：内核只提供机制：实现的 `ctx.park({ schema, payload })` 让当前 Run 转 `waiting`，对外接口 `unpark` / `withdraw` 送值或撤回。Operation 形式 `harness_park` 在 stdlib 自带的 harness 插件里（`stdlib/plugins/harness`），装配时按需装载。装饰器的 `ctx` 没有 `park()`：装饰器要挂起就 `ctx.call("harness_park", …)`，好让外层装饰器（如无人值守的短路）看得到。
- **原因**：注册表里的 Operation 全部来自装载的插件，内核不带原语。
- **影响**：原生插件的实现可以直接 `ctx.park` 挂起自己的 Run，不经 park Operation，装饰器看不到这次挂起（原生插件本就是受信的内侧代码）。
- **代码**：`stdlib/kernel/kernel.ts`（park、unpark、withdraw）、`run.ts`（Ctx.park）、`chain.ts`（DecoratorCtx）、`stdlib/plugins/harness/index.ts`。

### 11. 恢复靠写前日志，没结束的树都能恢复

- **方案**：树空闲时写快照、活跃前删，只恢复空闲的树；任意步续跑交给工作流引擎（3.6、11.4、R11、R29）；装配配置 `snapshotDir`。
- **实现**：每棵树一个只追加的日志，放在内核专属目录（装配配置 `journalDir`）。日志是事件流的持久投影：每条事件先过提交阶段，由它推出日志行同步落盘，再交给订阅者与插件，内核才往下走；插件看不到这一步，也拦不了。调用发起、调用完成、park 关闭，都这样先落盘再继续；树结束或被取消时删，关停时保留。启动（`kernel.boot()`）时重建所有没结束的树：已完成的调用回放；崩溃时正在执行的 Run 用原 runId 重新执行，并经 `ctx.attempt` 告诉它这是第几次执行。要落日志、要恢复的东西一律经 Operation 取：时间这类不确定的值调 `time_now`，状态将来是 state 插件的 Operation（存储由插件自己管）；调用结果本就记进日志、重放时回送，内核不另设接口。
- **原因**：崩溃时正在执行的原语（比如发邮件）有没有生效，只有它自己知道。内核给出信号和稳定的 runId（可当幂等键），由原语决定查重、跳过还是重做，与 Temporal 的 attempt、Stripe 的 Idempotency-Key 同理。
- **影响**：每次调用多两次同步写盘；写原语要考虑 `attempt > 1`，不处理时语义是「至少执行一次」；日志随树增长，长期存在的树以后要压缩。内核仍不做重试策略与补偿。
- **代码**：`stdlib/kernel/journal.ts`（commit）、`events.ts`（EventStream 的提交阶段）、`kernel.ts`（recover、callChild、park）。

### 12. 插件是工厂函数；生命周期与事件挂点是插件对象上的方法

- **方案**：插件包导出函数即 Operation，`setup(config)` 拿配置（6.1、附 A）；插件经 `@on` 处理器订阅事件；启动、关停各有 `harness.started`、`harness.stopping` 责任链（9.2）。
- **实现**：插件包默认导出 `plugin((config) => 插件对象)`。装载时以装配配置调一次工厂，工厂里的变量就是这个插件实例自己的状态（一个内核一份），工厂本身也就是 `setup(config)`。插件对象里放：
  - `requires`：依赖的插件。缺了启动失败；插件按依赖拓扑排序（同级按装载顺序），有环启动失败。只做检查与排序，不自动装载：装什么仍由装配侧决定；
  - `order`：按事件挂点调整先后，如 `{ beforeRunStart: { before: ["ui"] } }` 把自己在这个挂点上排到 ui 前面。事件挂点缺省依赖（含间接的）在前；`before` 里的排在自己之后，`after` 里的排在自己之前；没装的插件忽略，排出环启动失败。`onStart` / `onStop` 不能调：依赖必须先启动、后关停；
  - `operations`、`decorators`：声明（见 2），名字取 `包名_键名`；
  - `onStart()`：启动时（`kernel.boot()`）按依赖的先后逐个 await，抛异常则启动失败；之后才恢复没结束的树、开始接受调用；
  - `afterStart()`：启动完成后（树已恢复）通知；
  - `onStop()`：关停时，在途的树杀掉之后，按依赖的逆序逐个 await（依赖后关）；
  - `after*(event)`：每种事件恰好对应一个方法（`afterRunStart`、`afterRunExit`、`afterRunKill`、`afterCallReject`、`afterParkOpen`、`afterParkClose`、`afterTreeRecover`，三种装饰器事件合为 `afterDecorate`），只读通知；
  - `afterAny(event)`：所有事件，投递、观测类插件用；
  - `before*(event)`：能拦的挂点，转换发生之前同步调，拿到将要发出的事件，返回 `{ veto: 原因 }` 即拦下：`beforeRunStart`（子调用以拒绝返回、不建子 Run；外部调用抛异常）、`beforeRunExit`（结果换成拒绝）、`beforeParkOpen`（不等待，park 直接以拒绝关闭）、`beforeParkClose`（外部送值或撤回抛异常，park 照旧等待）、`beforeTreeRecover`（这棵树不恢复）。

  没实现的方法不调。插件对象里有不认得的键（比如挂点方法名拼错）时装载即报错。
- **原因**：游戏引擎式的脚本挂点：插件想接哪个时机就实现哪个方法，一个对象就是插件的全部；工厂给每个内核实例一份独立的状态，配置不再走全局的环境变量。装饰器保留：它在 Run 里面、可回放、包住一次调用（审批的 park、计时、预算的预留与结算）、按 Operation 自选并有顺序；挂点是 Run 外面的全局时机。
- **影响**：方案 R14 要求全局行为由装配侧决定，插件不能因为注册了什么就改变全局行为。`before*` 能拦所有调用，是全局的；这里由装配侧决定装不装这个插件来体现。只有原生插件有挂点，script 包没有。
- **代码**：`stdlib/kernel/plugin.ts`（plugin、AFTER、BEFORE、PluginObject）、`kernel.ts`（use、boot、arrange、stop、before、dispatch）、`order.ts`（topo）、`loader.ts`。

### 13. 代码组织：`stdlib` 框架包与 `app`

- **方案**：插件与 script 包从 `harness` 包 import 运行时函数（`call`、`emit`、`spawn`）与内核的 Operation（`harness.park`、`harness.exec`）（3.1、附 A「`harness` 包」）；别的包 `import { read } from "fs"`。
- **实现**：
  - `stdlib/` 是框架包，import 名就是 `stdlib`（`tsconfig.json` 的 `paths`，Bun 运行时同样认）。`stdlib/index.ts` 是唯一的公开入口：写包用的 `op` / `decorator` / `plugin`（插件）、`script`（script 包，见 17）、`opaque` 与 `Ctx`、`Result` 等类型，搭应用用的宿主 `host` 与装配配置 `Assembly`（见 15）；`Kernel`、`loadPlugin`、`loadScript` 给测试与自己搭宿主用。内核在 `stdlib/kernel/` 下，其余模块（日志、回放、入口的声明 `entry` 等）不导出。
  - stdlib 自带的插件在 `stdlib/plugins/` 下，按领域分包：`harness`（`harness_park`、`harness_exec`，即方案的 `harness.park`、`harness.exec`，见 18）、`time`（`time_now`）、`ui`（给人看的问题的约定格式与审批，见三）、`kv`（按调用方的包分开的键值存储，script 包存状态用，见 17）、`package`（装上 script 包，见 20）、`fs`（工作区里的文件操作）、`model`（调模型、压缩历史）。`fs`、`model` 原是 MVP 自己的插件（实现见三），第二个应用 `app/sandbox` 也要用，移进 stdlib。基建的接口与实现在 `stdlib/infra/` 下（见 16）；script 包的打包与解释器在 `stdlib/script/` 下（见 17）；服务接口在 `stdlib/serve/` 下：`http`，由宿主按装配配置 `serve` 启停（见 15）。stdlib 里没有客户端：客户端在 Harness 外面、经服务接口用它（见 15）。各应用共用的 HTTP 客户端与终端界面在 `client/`，与 `stdlib/` 平级、不属于 Harness，import 名 `client/…`（同样经 `tsconfig.json` 的 `paths`）；应用的客户端只写自己的配置：连哪、说话调哪个 Operation、Run 树里怎么摘要。
  - `app/` 下是用 stdlib 搭出来的应用，各自有服务端与客户端；`app/mvp` 演示怎么搭：`server/` 是它的 Harness（`server/main.ts` 只有装配配置，`server/scripts/` 是它的 script 包；用到的插件都是 stdlib 的，应用自己的插件也可以放在 `server/plugins/`），`client/` 是它的客户端（`main.ts` 配好终端界面，`brief.ts` 是 Run 树里的摘要规则），`start.ts` 把两边一起起，`paths.ts` 是两边共用的状态目录与 socket 位置。`app/sandbox` 是第二个应用：跑在 E2B 沙盒里的通用 Harness，当用户的小服务器、自带管理 agent，目标与分步见 `doc/沙盒应用.md`；结构同 MVP，两边共用的配置在 `config.ts`。
  - 每个应用一份 `tsconfig.json`（继承根配置），只编译这个应用，它的装配类型不影响 stdlib 与别的应用（见 14）。
  - 运行时函数在 `ctx` 上（见 3），不从包里 import。
- **原因**：框架与应用分开，应用怎么搭一目了然；import 不再写一串 `../`。
- **代码**：`stdlib/index.ts`、`tsconfig.json`、`stdlib/plugins/`、`stdlib/serve/`、`stdlib/host.ts`、`client/`、`app/mvp/`、`app/sandbox/`。

### 14. 调用的类型从插件源码推出，由应用登记

- **方案**：包的 d.ts 由同一个工具在构建期从 TS 类型生成（7.3、R19）；插件之间 `import { read } from "fs"`，打包时换成按名字的调用（3.1、6.2）。
- **实现**：
  - `op()` 记下入参的类型（`z.input`，即调用方要填的形状，带默认值的字段可不填）与出参的类型（实现的返回值），`plugin()` 记下插件对象的具体类型。
  - 用 `import type` 把包登记进 `Packages`（`declare module "stdlib"`）：stdlib 自带的由 stdlib 登记（`stdlib/plugins/packages.ts`，`stdlib/index.ts` 以三斜线引用），用 stdlib 的都有这些类型；应用只登记自己的插件与 script 包（`app/mvp/server/packages.ts`）。不手写 d.ts，运行时什么也不加载。
  - 插件里写 `ctx.ops.fs.read({ path })`：包或 Operation 不在注册表里、入参不对，编译即报错；结果带类型，编辑器能补全。
  - `ctx.call(name, input)`：名字在注册表里时同样带类型；名字是变量（模型挑的工具）或不在注册表里（测试里临时注册的）时，入参与结果是 `unknown`，不报错。
  - 运行时 `ctx.ops.fs.read(x)` 就是 `ctx.call("fs_read", x)`，照常过装饰器、能力面、日志与事件，事件与日志里的名字不变。
- **原因**：类型与实现同源，不会对不上；不需要构建步骤；显式 `ctx` 下也能像调包里的函数一样读写。
- **影响**：
  - 类型只是契约：不知道能力面，也不知道这次装没装，这两样仍由运行时拒绝。
  - 装饰器改写的结果不反映在类型上（如 `ui_approval` 带说明时把结果包成 `{ result, userNote }`）。
  - 插件的出参若由调用自己包里 Operation 的结果推出，类型会绕成环，要给 `impl` 标返回类型。
  - `ctx.call` 不补全名字、拼错不报错：它只查名字里的那个包，查全表会把调用方自己的包卷进来、绕成环。写死的调用用 `ctx.ops`。
  - 装配类型文件要与装配配置里装载的插件保持一致，以后由装配配置生成；给 script 包（QuickJS）的 d.ts 也可以从这份注册表生成。
- **代码**：`stdlib/kernel/ops.ts`、`plugin.ts`（op、plugin）、`run.ts`（Ctx、Result）、`stdlib/plugins/packages.ts`、`app/mvp/server/packages.ts`、`app/mvp/tsconfig.json`；类型检查 `app/mvp/server/packages.check.ts`。

### 15. 宿主与服务接口：对外接口只交给服务接口，启停只归宿主

- **方案**：Harness 的对外接口（调用、`unpark` / `withdraw`、取消、收割）由外部使用，外侧只能调公开表里的 Operation（1.4、7.2、附 A）；没说由谁在进程里把外面的请求接进来，也没说进程由谁启停。
- **实现**：
  - **宿主**（`stdlib/host.ts`）：一个进程一个 Harness，只有它握着内核。`host(装配配置)` 先占住服务接口要监听的地址（被占了即同一个状态目录已有 Harness 在跑，不往下启动、不碰日志），再建内核、按顺序装载插件、启动（恢复上次的树），然后让服务接口开始监听。收到 SIGINT / SIGTERM 就优雅关停：服务接口先停止接新连接，内核等在途的调用跑完（最多 `graceMs`，缺省 10 秒），关停中再收到一次就强杀；内核关停完断开连接、退出进程。启停是机器的信号，插件碰不到。
  - **服务接口**（`stdlib/serve/`）：Harness 对外提供服务的协议层，由装配配置的 `serve` 决定开哪些、监听在哪、对外哪些 Operation（`expose`），与 `plugins`（能力）分开：前者跟着部署走，后者跟着应用走。看装配配置就知道对外了什么；不在 `expose` 里的一律当作没有。现在有 HTTP（见二的「HTTP 服务接口」）；以后 gRPC 等也加在这里。只在 stdlib 里写，对外接口只交给它们。
  - **对外接口 `outside`**（`stdlib/kernel/outside.ts`）：`submit`（只能调声明了 `api` 的 Operation）、`wait`（等结束，不取走）、`reap`（取走结果）、`runs`（结果还没被取走的树）、`parks`（等待中的问题）、`unpark`、`withdraw`、`operations`（对外的 Operation 与入参 JSON Schema）。经它发起的树，根记下 `origin`（谁发起的；HTTP 是 `http` 或 `http:客户端自报的名字`），进 `run.started`、日志的根行与 `tree.recovered`，重启后还在。
  - **根的结果留到被取走**：调用方可能不在（断开、关了 UI、中途重启），所以根 Run 结束时结果写进日志（`exit` 行），取走（`reap`）才删；关停时被杀的树不算结束，重启后接着做；没人取的放 `resultTtlMs`（缺省 7 天）后在启动时清掉。见二的「收割」。
  - **`api` 与 `expose`**：插件给自己的 Operation 声明 `api: true`，表示它适合对外（比如 `kv_set` 会整个替换一个键，就不该声明）；对不对外由装配配置里各服务接口的 `expose` 决定，只能列 `api` 的：写在 `main.ts` 里，名字由注册表推出（`ApiName`），拼错或不是 `api` 的类型检查即报错，启动前再查一遍，不对就启动失败。`api` 与 `public` 分开：`public` 是进公开表（script 包能调，缺省也交给模型当工具，见 7、17），`api` 是能对外，比如 `fs_write` 公开而不对外——方案的公开表在这里分成两张。
  - **对外的契约**：`api` 的 Operation 必须写 `usage` 与出参 schema `output`，注册时检查；入参与出参都须能转成 JSON Schema，由 `GET /operations` 给出。写了 `output` 的 Operation（不限于 `api`）返回前按它校验：对不上算它自己失败（`invalid output`），对得上交出解析后的值。
  - 宿主与测试直接调内核：`kernel.submit`（原名 `start`，免得与开机混淆）什么都能调，不记 `origin`。
  - **客户端**（应用的，如 `app/mvp/client/`）：UI 与别的系统都在 Harness 外面，经服务接口用它，不属于 Harness 的哪一层，所以不在 stdlib 里：应用有自己的服务端（它的 Harness）与客户端。共用的部分在 `client/`（第二个应用 `app/sandbox` 也要用时从 `app/mvp/client/` 抽出来）：`httpClient({ socket } 或 { url, token }, name)` 经 Unix socket 或 URL（TCP，可带令牌）调服务接口（调用、取结果、列出没取走的结果与在等的问题、回答、订阅事件流），`name` 记进它发起的树的 origin（`http:名字`）；终端界面 `runConsole` 建在它上面（见三的「终端对话」）。宿主一直跑到收到信号，不随哪个客户端走而停。
- **原因**：应用的逻辑都写成插件，`app/mvp/server/main.ts` 只剩装配配置。插件的权限就是 stdlib 给的那些：Run 里的 `ctx`、事件挂点、给自己的 Operation 声明 `api`；能从外面发起调用、回答问题的只有 stdlib 的服务接口；进程启停只在宿主。插件写完、声明 `api`，就是一个 API。UI（终端、网页）与别的系统都是客户端，走同一套服务接口。
- **影响**：
  - 原生插件与内核在同一个进程里，技术上能 import 任何东西；这里约束的是 harness 层面的权限，代码层面靠 review 与 lint（6.4），真正不可信的代码走 script 包。
  - 新协议只能加在 stdlib 里，应用不能自带。
  - 认证只有一个令牌：TCP 上配了 `token`，每个请求都要带 `authorization: Bearer <令牌>`；绑到本机以外（如沙盒里的 0.0.0.0）必须配，不配启动即失败。Unix socket 靠文件权限（只给本用户）。持令牌的什么都能做，`runs`、`parks`、事件流都是全量的；以后按调用方分权限再过滤。
  - 只有开了 Unix socket 时才能挡住同一个状态目录上的第二个 Harness；写前日志本身还没有锁。
  - 后续：自举用的 `harness_restart`——这次调用先完成、写进日志，宿主再以约定的退出码退出，由外层重新拉起，调它的树用新代码接着做；没先写进日志的话，恢复时会再调一次，无限重启。
- **代码**：`stdlib/host.ts`、`stdlib/serve/`、`stdlib/kernel/outside.ts`、`kernel.ts`（submit、outside、wait、reap、runs、parks、recover）、`journal.ts`（exit 行、run.reaped）。测试 `stdlib/host.test.ts`、`stdlib/serve/http.test.ts`、`stdlib/kernel/outside.test.ts`；客户端在 `app/mvp/client/`，测试 `client/http.test.ts`、`client/console/*.test.ts`。

### 16. 四层与基建：插件不直接做 IO，基建由装配提供、宿主注入

- **方案**：插件在 `setup` 里 `provides` / `require` 服务，服务名描述能干什么（`model-backend`、`store`、`isolate`），按消费方创建、隔离由提供方负责（6.3、6.4、R17、附 A「服务名」）；没有把整体分层写出来。
- **实现**：装配配置按四层写（`app/mvp/server/main.ts`）：
  - **接口**（`serve`）：哪些 Operation 怎么对外（见 15）。
  - **应用**（`scripts`）：编排，比如 agent 循环、对话（`agent`、`chat`）。是 script 包：只能调公开的 Operation，不碰基建（见 17）。
  - **领域**（`plugins`）：插件，整合某个领域（`fs`、`model`、`ui`、`kv`…）。
  - **基建**（`infra`，`stdlib/infra/`）：Harness 外面给的能力，由装配配置建好、宿主管启停：
    - `llm`：模型后端（`Llm`：`complete(context)`，消息与工具用 pi-ai 的格式，用户消息与工具结果里可以有图片；模型看不了图的，实现把图片换成占位文字，不交给它）。实现 `piLlm({ model })` 经 pi-ai 调，「provider/模型 id」建的时候就找、配错装配即失败；key 由 provider 从环境变量读；看不看得了图按 pi-ai 的模型信息，换占位文字这一步自己做，不依赖 pi-ai 各家接口的实现。
    - `workspace`：工作区（`Volume`）。
    - `state`：持久状态（`Volume`），宿主切成互不相干的几块：内核的写前日志在 `journal/`；每个插件的存储在 `store/<包名>/`。
  - **存储的抽象 `Volume`**：按相对路径 `read` / `write`（整个替换，不留半截）/ `stat` / `list` / `mkdir` / `glob`，`sub(path)` 取一个子目录当作独立的一块；越不出去（`..`、绝对路径、指向外面的符号链接都拒绝），出错信息里只有相对路径。`open` / `close` 由宿主在启动前、关停最后调。`localPath` 是它在本地文件系统上的目录，没有就是纯远程的。实现现在只有 `localDir(root)`（本地目录，也适用于已挂好的 FUSE、NFS 目录）；换成 rclone+FUSE 时写一个实现，`open` 里起 `rclone mount` 等它挂好、`close` 里卸下，其余照本地目录、`localPath` 是挂载点；对象存储可以直接实现这些方法，没有 `localPath`。插件不用改。
  - **注入**：插件写 `plugin({ needs: ["llm"] }, (config, { llm }) => …)`，装载时只注入它声明的，装配没提供就装载失败；有就用、没有也能装的写在 `wants` 里（如 harness 插件的 `workspace`，没有时它跑不了包草稿，见 18）。能声明的是 `llm`、`workspace`、`store`（持久状态里属于它的那一块，看不到别的插件的，也碰不到写前日志），以及宿主自己给的 `scripts`（装 script 包，见 20）。
  - **用到本地路径的**：写前日志要同步写、fsync，要求 `state` 有 `localPath`，没有就启动失败；`fs_grep` 要让 ripgrep 扫真实文件，工作区没有 `localPath` 时以拒绝返回，别的文件工具照常（以后的 bash 同理）。
  - **检查**：插件与内核在同一个进程里挡不住 `import`，所以 `stdlib/plugins/layers.test.ts` 查 stdlib 的插件（应用自己的插件也要这样查）：不许 import `fs`、`child_process`、`net`、`http` 等，不许在运行时 import 模型 SDK（`import type` 可以），不许 `fetch`、读 `process.env`、用 `Bun.file` / `Bun.spawn` 之类。script 包不用查：打包与解释器挡住了，见 17。
- **原因**：换基建（本地目录换成挂载的远程存储、换模型供应商、换凭据的来处）只改装配配置；插件拿得到什么一目了然，权限就是 stdlib 给的加上装配注入的；凭据与供应商只在基建层。方案的服务按名字解析、按消费方创建，这里先只有宿主提供的这几种，插件之间还不互相提供服务。
- **影响**：
  - 写前日志的持久性取决于 `state` 的实现：本地盘照 fsync；rclone+FUSE 的写先落本地缓存再上传，进程或沙箱没了时缓存里还没传的会丢——写前日志宜放在真正持久的本地盘或持久卷上。
  - Unix socket 也要在本地文件系统上：`state` 换成挂载的远程存储时，socket 另放。
  - `stdlib` 的入口只导出基建的类型；实现按路径 import（`stdlib/infra/volume`、`stdlib/infra/llm`），免得每个插件 import `stdlib` 都带上模型 SDK。
- **代码**：`stdlib/infra/`（`index.ts` 的 `grant`、`journalDir`，`volume.ts`，`llm.ts`）、`plugin.ts`（plugin 的 needs）、`loader.ts`、`host.ts`；`app/mvp/server/main.ts`、`stdlib/plugins/fs/operations.ts`、`stdlib/plugins/layers.test.ts`。测试 `stdlib/infra/*.test.ts`。

### 17. 应用层：script 包在 QuickJS 里跑

- **方案**：script 包是外侧：导出函数即 Operation，导出的全部进公开表；只能经内核给的入口调公开表里的 Operation，不能做 IO；Bun 转译、把包内模块与纯 JS 依赖打成一个文件，在内核内嵌的解释器（QuickJS 编译成 WASM）里跑，每个 Run 一个新实例，有内存与单段同步执行的上限，`Date.now()` 与 `Math.random()` 由内核提供、随调用记录回放；可以贡献装饰器与处理器；声明写在 JSDoc，d.ts 与 JSON Schema 发布时生成（3.1、7.2、7.3、7.5、R5、R6、R7、R20）。
- **实现**：
  - **声明**：包的默认导出是 `script({ requires?, operations })`，Operation 照常用 `op()` 写。没有装饰器、挂点、基建，也没有配置：人设、阈值写成包里的常量，要改就复制一份。装配配置里列在 `scripts`，在插件之后由 `loadScript` 装载。
  - **只贡献 Operation，不做装饰器与处理器**（方案里 script 包也贡献装饰器与处理器，7.3）：
    - 装饰器：方案只许它被 script Operation 自己引用，不进默认集，不包原生的 Operation，所以它能包住的只有作者自己的 Operation，等于包内复用一段前后逻辑——写成包内的普通函数即可。要包住别人的横切逻辑（审批、预算、审核、记忆召回）本来就该是可信的原生插件。它唯一的特权是写 `run.context`（R24 规定只有装饰器能写）；做 `run.context` 时改成由调用方显式交给 `model_complete`，同样不动历史前缀。
    - 处理器：方案里它只读、不能 `call`，要做事只能 `spawn`。触发点在自己代码里的（如每轮对话后整理记忆），在那里直接 `spawn` 就行；只有要对别人的事件作出反应（如每次 `fs_write` 记审计）才需要处理器，那是全局行为，由装配配置列出。出现这类需求再做（`spawn` 见 21）。
  - **打包**（`stdlib/script/bundle.ts`）：Bun 打成一个脚本，包里的模块与文本资源（`with { type: "text" }`）内联。`import "stdlib"` 换成解释器里的那份（只有 `op`、`opaque`、`script`、`image`、`isToolContent`；import 了别的如 `plugin`、`host`，打包即失败），`import "zod"` 换成解释器里的那份；别的 import（Node 内置模块、npm 包、包外的文件）打包即失败。`import type` 转译时去掉，不限。
  - **解释器**（`stdlib/script/sandbox.ts`）：QuickJS-NG 编译成 WASM（`quickjs-wasi`，pi 也用它，版本钉在 3.6.2）。底子是运行时（`stdlib/script/inside/runtime.ts`）连同 Zod 求值一次存成的快照，每个进程建一次。装载时从底子恢复、求值包的代码，读出声明：入参与出参的 JSON Schema 由包自己的 Zod 在解释器里生成，内核给模型与对外的原样用它，校验用 `z.fromJSONSchema` 转回的 Zod（方案：每次调用按 schema 校验入参）。包的代码不在宿主里执行。每个 Run 从底子恢复出一个全新的 WASM 实例（内存与别的 Run 不共享），求值包的代码，执行；结束或被杀即丢掉，模块级的变量不跨 Run。
  - **解释器里有什么**：语言本身、`stdlib` 与 `zod`、`TextEncoder` / `TextDecoder`。`ctx` 有 `runId`、`attempt`、`callerPackage`、`call`、`ops`、`spawn`（见 21）、`tools()`；`park` 以拒绝返回，没有 `signal`。调用经宿主函数交给内核，记在这个 Run 名下，照常查能力面与公开表、记日志、恢复时回放；入参与结果以 JSON 往返。没有文件、网络、子进程、定时器、`process` / `Bun` / `fetch`；`Date.now()`、`new Date()`、`Math.random()`、`performance` 拿掉了（抛异常），要时间调 `time_now`。`console` 的输出经 `ctx.log` 记成这个 Run 的日志（`run.logged` 事件，见二），不交给调用方；每次执行最多约 10 万字，再多的不记。
  - **限额**：内存 256 MB；一段同步执行（两次等待之间）超过 1 秒即中断；求值包的代码 1 秒。超出、或解释器陷入（如递归太深），这个 Run 以失败结束，原因是超出的那条。
  - **内核查的**（进程里与解释器里一样）：script 包的 Operation 都公开，所以都得写 `usage`（写 `public: false` 装载失败）。它的实现发起的调用，目标不在公开表里的以内核的拒绝返回（`x is not public: … is a script`），与能力面一样不建子 Run、发 `call.rejected`；`ctx.park` 以拒绝返回——要挂起就调 Operation。装饰器发起的调用不查（装饰器都是插件的）。测试可以直接 `kernel.useScript` 交进程里的实现，规则相同。
  - **存状态**：`kv` 插件（stdlib）按调用方所在的包分开：`kv_get` / `kv_set`，一个键一个 JSON 文件，存在 kv 自己那块持久存储下的 `<包名>/<键>.json`；内核给每个 Run 的 `ctx.callerPackage`（父 Run 的 Operation 所在的包）就是为它加的。外部直接调 kv（没有调用方的包）失败。
  - MVP 的 `agent`、`chat` 在 `app/mvp/server/scripts/`：`agent` 调 `model_*`、`time_now` 与模型挑的工具；`chat` 调 `kv_*` 与 `agent_assist`。为此 `model_complete`、`model_compact`、`time_now` 改成公开、`tool: false`（见 7）。
- **原因**：应用层就是方案的 script 层：写法、能调什么、隔离都照方案；能调什么由提供方的 `public` 决定。快照让每个 Run 一个新实例也便宜。
- **影响**：
  - 开销（这台机器）：底子约 0.25 秒（Zod 在解释器里求值约 0.15 秒），每个进程一次；每个包装载约 25 毫秒；每个 Run 约 10～15 毫秒（恢复快照、求值包的代码）。底子的快照缓存在磁盘上（`node_modules/.cache/harness/`，键是底子的代码与解释器 WASM 的摘要，换了 Zod、运行时或 quickjs-wasi 就重建；读不了、恢复不对也重建），再启动时读回来，约 0.04 秒。MVP 的启动：没有 QuickJS 时约 0.35 秒，有了约 0.65 秒，缓存后约 0.47 秒。
  - 交进交出的 JSON 在解释器里解析与生成，每 MB 约 10 毫秒；带几 MB 图片的历史，一轮约 0.3 秒。宿主交给解释器的按 UTF-8 字节传、在解释器里解码：`quickjs-wasi` 的 `newString` 对大字符串很慢（5 MB 约 0.3 秒）。同步执行的上限因此放宽到 1 秒，方案是几十毫秒。
  - 时间与随机数还不由内核提供（方案的做法：WASI 的时钟可以接管，取值记进日志、恢复时回放）；script 包经 `time_now` 取时间，每次是一个子调用；还没有随机数。
  - 还没有：script Operation 引用装饰器的限制（方案只许引用公开的）、调用的因果 `after`（R21）、包里的纯 JS 库（现在只认 stdlib、zod）、日志输出（以后经事件）。
  - script 包的 Operation 都公开，缺省也会交给模型当工具：调用方用能力面收窄（`agent` 只开 `fs`、`model`、`ui`、`time`）。
  - `kv` 按调用方的直接父 Run 分包：装饰器发起的调用记在被装饰 Run 名下，读写的是被装饰 Operation 所在包的数据。
  - 之前 chat 的对话历史在 `store/chat/conversation.json`（`{ history }`），现在在 `store/kv/chat/conversation.json`（数组），不迁移；在途的旧树重启后比对不上（原来调 `chat_load`），移到 `diverged/`。
- **代码**：`stdlib/script/`（`bundle.ts`、`sandbox.ts`、`inside/`）、`stdlib/kernel/plugin.ts`（script、opaque、tool）、`kernel.ts`（useScript、callChild、execute 的 park 与 callerPackage、toolsIn、register 的 schemas、产物摘要的 source）、`loader.ts`（loadScript）、`host.ts`（scripts）、`stdlib/plugins/kv/`；`app/mvp/server/scripts/`。测试 `stdlib/script/sandbox.test.ts`、`stdlib/kernel/script.test.ts`、`stdlib/plugins/kv/kv.test.ts`。

### 18. 临时脚本：`harness_exec`

- **方案**：模型或编排助手对着 d.ts 写一段脚本交给 `harness.exec`，一次跑完：给源码时默认导出入口函数；也可以给工作区里的包草稿目录与要运行的导出函数。`harness.exec` 为它建一个 script 形态的子 Run，能力面按 script 规则计算，收窄只来自入口函数的 JSDoc（7.5、附 A）。
- **实现**：
  - harness 插件的 `harness_exec`，公开，模型直接当工具用。两种用法：
    - `{ source, input? }`：一段源码（TypeScript 或 JavaScript），默认导出 `async (ctx, input) => 结果`；`ctx` 与 script 包的一样（`ctx.call` / `ctx.ops`，结果是 `{ ok, value }` 或拒绝）。只能 import `stdlib`、`zod`。
    - `{ dir, operation, input? }`：工作区里一个 script 包草稿（写法同装上的包），跑它的 Operation `operation`：与装载一样打包整个目录（包里的文件可以互相 import，文本资源内联），读出声明，按它的 schema 校验入参与出参。草稿没有装进内核，它的 `requires`、`only`、`exclude` 不起作用。目录须在工作区里，包里的文件按解开符号链接后的真实路径查，指到外面的不打包；打包要读真实文件，工作区须有本地路径。harness 插件用 `wants` 拿工作区，装配没给工作区时这种用法以拒绝返回。
  - 跑的就是 `harness_exec` 这个 Run，不另建子 Run：它声明 `script: true`（`op()` 的新字段：实现跑的是 script 代码），发起的调用按 script 的规则只能调公开的。在全新的解释器里跑，限额同 script 包（见 17）。调用记在这个 Run 名下，照常过装饰器（如 `fs_write` 的审批）、记日志；恢复时源码重新跑，已完成的调用回放。
  - 能力面是公开表的全部，不继承调用方的收窄（方案如此；收窄不承担安全，R13）。
  - 出参是脚本的返回值（没有即 `null`）。`console` 的输出不交回，记成这个 Run 的日志（`run.logged`），终端画在 Run 树里。源码写错、import 了不许的、默认导出不是函数、草稿里没有这个 Operation，以拒绝返回，原因带行列。
  - 一次最多发起 100 个调用，再调 `ctx.call` 抛异常：还没有预算插件，先防一段脚本没完没了地调。
  - MVP 的 `agent` 在能力面里加了 `harness_exec`，人设加了一句：要连着调很多次工具（批量读、统计、按结果分支）时，写一段脚本一次做完。
- **原因**：模型一轮只能发几个工具调用，批量与按结果分支的事要来回很多轮；写成脚本一次做完，省模型请求与 token，中间结果也不进历史。真模型试过：统计工作区里 5 个 `.md` 文件各有几行，它先用一段脚本找文件，再用一段脚本读完并统计，一共 3 次模型请求，结果正确；让它在 `drafts/stats` 写一个统计用的 script 包草稿再试跑，它写好、按报错改了几次，用草稿的用法跑通，打印的每行出现在 Run 树里。
- **影响**：
  - 模型经它调得到收窄之外的公开 Operation：`tool: false` 的（如 `model_complete`），别的 script 包的（如 `chat_say`）。公开表本来如此；要拦的靠不公开、靠装饰器。
  - 脚本的中间结果不进模型的历史，只有出参进；草稿里用 `kv` 存的数据在 `harness` 名下（调用方的包），装上之后在包自己名下。
- **代码**：`stdlib/plugins/harness/index.ts`（exec）、`stdlib/script/sandbox.ts`（runSource、runDraft）、`bundle.ts`（bundleSource、按真实路径查包里的文件）、`inside/runtime.ts`（run 的默认导出、console）、`stdlib/kernel/plugin.ts`（op 的 script、plugin 的 wants）、`stdlib/infra/index.ts`（grant 的 wants）；`app/mvp/server/scripts/agent/index.ts`。测试 `stdlib/plugins/harness/exec.test.ts`。

### 19. script 包运行中重新装载

- **方案**：script 包随产物发布，增改不用重建二进制（7.1）；没说运行中的 Harness 怎么换上新的。
- **实现**：
  - 内核 `installScript(pkg, object)`：运行中装上一个 script 包，或把装上的整个换成新的（见 20）。之后的调用用新的；正在跑的 Run 用旧的跑完（它们拿着旧的实现）；新的里没有了的 Operation，之后调用即 `unknown operation`。新的有问题（名字不合规则、键不认得、依赖没装、`usage` 没写、引用的装饰器不在）就抛异常，旧的照旧。插件不能换。
  - 装配配置 `watch: true` 时，宿主盯着 `scripts` 的目录（含子目录）：文件变了，等 0.1 秒（一次保存常有几个改动）重新打包、读声明、换进内核，一个接一个地换。对外（`expose`）的 Operation 在新的里不再是 `api` 的，不换。结果打在标准错误上：`harness：script 包 chat 改过了，已重新装载`，或 `……重新装载失败，仍用原来的：原因`。
  - MVP 开着 `watch`：改了 `app/mvp/server/scripts/` 里的包，运行中的 Harness 接着就用新的；改了 `plugins/` 要重启。
- **原因**：应用层的迭代不用重启 Harness，也不打断在途的对话。
- **影响**：
  - 产物摘要随之改变。换代码之前开始、之后崩溃的树，恢复时用新代码重新执行，走的路不同就按对不上处理（移到 `diverged/`）。
  - 结果只在标准错误上，还不是事件；连着的客户端看不到。
- **代码**：`stdlib/kernel/kernel.ts`（installScript）、`stdlib/host.ts`（watch、watchScript）；`app/mvp/server/main.ts`。测试 `stdlib/kernel/script.test.ts`、`stdlib/host.test.ts`。

### 20. 装上试好的 script 包：`package_install`

- **方案**：script 包随产物发布，使用者写的包上架经审核（7.1、7.4、P4）；agent 现场生成的包与预设的过同一个校验器。没写运行中的 Harness 怎么装上一个新包。
- **实现**：
  - **放哪**：装上的包在持久状态的 `scripts/<包名>/` 下（`STATE_DIR/scripts/`），与装配配置分开：装配配置是代码，装上的是状态。启动时在装配的 script 包之后装载；装不上的（写坏了、与装配里的包同名）跳过，打在标准错误上，不挡启动。
  - **怎么装**：宿主建一份「装上的 script 包」（`stdlib/script/installed.ts`），把其中的 `scripts`（`install(包名, 来源目录)`）当作基建交给声明需要它的插件——插件拿不到内核，只拿到这一件事。装的时候先把文件拷到临时目录（不拷点开头的；最多 200 个文件、5 MB），在解释器里装载一遍，过了才换到 `scripts/<包名>/`，再换进内核（`installScript`，新装或换掉同名的，正在跑的 Run 用旧的跑完）；内核不收就把盘上的换回去。名字须合包名规则，不能与装配里的包（插件、装配的 script 包）同名：要改它们改装配。
  - **谁来装**：stdlib 的 `package` 插件，`package_install({ dir, name? })`：工作区里的草稿目录（`index.ts` 须在工作区里），包名缺省取目录名，返回装上的 Operation 名。它用 `ui_approval`，装之前问人。`harness` 插件不能用它：`ui` 依赖 `harness`，会绕成环，所以单独一个插件。
  - MVP 装了 `package` 插件，`agent` 的能力面加了 `package_install`，人设加了一句：要写 script 包时，在工作区里写草稿，用 `harness_exec` 试跑，跑通了再装上。
- **原因**：agent 自己写、自己试、自己装，人只在装的时候点头；代码不出工作区与持久状态，不碰应用的源码，Harness 不用重启。真模型试过：让它写一个统计 `.md` 文件的包 `mdstats`，它写草稿、试跑（第一版没写对，碰到「最多调 100 次」停下，它用几段脚本查清原因改好）、装上；重启 Harness 后 `mdstats_count` 还在，调用结果正确。
- **影响**：
  - 装上的包的 Operation 公开，但不在 `agent` 的能力面里：模型经 `harness_exec` 调它们，或改 `agent` 的能力面。
  - 还没有卸载；装上的包也不受 `watch` 管（改它们要再装一次）。
  - 方案的上架审核、版本与回滚（11.x）还没有：现在就是问一次人。
- **代码**：`stdlib/script/installed.ts`、`stdlib/plugins/package/`、`stdlib/infra/index.ts`（Scripts、Provided）、`stdlib/host.ts`（建它、启动时装载）、`stdlib/kernel/kernel.ts`（installScript）；`app/mvp/server/main.ts`、`app/mvp/server/scripts/agent/index.ts`。测试 `stdlib/plugins/package/package.test.ts`、`stdlib/kernel/script.test.ts`。

### 21. 另起一棵树：`ctx.spawn`

- **方案**：`spawn(name, input)` 发起一棵新 Run 树，不等结果、不阻塞当前流程；新树没有父，根记下 `spawnedBy`，深度从发起方接着往下数；新树怎么记账、`spawn` 次数的配额交给 budget；自指排除：一个包用 `spawn` 发起的整棵树上，不装载它自己的装饰器与处理器；已发起的 `spawn` 记进调用记录，恢复时不再发起（5.3、3.6、9.5、R14）。
- **实现**：
  - `ctx.spawn(name, input)`：实现、装饰器、script（解释器里）都有。返回 `{ ok: true, value: 新树根的 runId }`。与 `ctx.call` 同样检查（目标存在、能力面、script 只能 spawn 公开的、保险丝、入参、`beforeRunStart`），被拒以拒绝返回、不起树，发 `call.rejected`（带 `spawn: true`）。
  - **新树**：根没有 `parent`。`run.started` 带 `spawnedBy`（发起方的 runId）、`step`（是发起方的第几步）、`skipDecorators`（见下），`depth` 是发起方的加一，深度保险丝照样管，自己 spawn 自己也停得下来。紧跟着发 `run.spawned`（`runId` 是发起方，`step`、`target`、`input`、`child`）。新树不算发起方的子 Run：发起方不等它，取消发起方不碰它；它能单独取消。
  - **结果没人取**：结束即丢，只在事件（`run.exited` / `run.killed`）里留下；不在 `runs()`（`GET /runs`）里，不能 `wait` / `reap`。它里面的 park 照常在 `parks()` 里，可以回答。要结果就让新树自己存（如 kv），或改用 `ctx.call`。
  - **不装载发起的包的装饰器**：实现发起的，是 Operation 所在的包；装饰器发起的，是装饰器所在的包。这个包的装饰器（默认的与自选的）不包新树上的调用。从新树里再 spawn 的，之前排除的接着排除（累积）：方案只排除发起的包自己，跨包的「A 的装饰器 spawn → B 的装饰器 spawn → A 的装饰器 spawn…」靠深度保险丝拦；累积后这种环第二层就停了。处理器还没有（见 17）。
  - **写前日志**：新树一个文件，root 行多记 `spawnedBy`、`step`、`depth`、`skipDecorators`。发起方的文件记一行 `spawn`（`seq`、目标、入参摘要、结果：新树的 runId 或拒绝），发起即完成，参与完成顺序。新树正常结束或被取消即删文件（没有 `exit` 行）；关停保留，重启后接着跑；对不上移到 `diverged/`。
  - **恢复**：新树与别的树一样恢复，但不在 `boot()` 返回的要收割的树里。发起方重新执行到 spawn 那一步：日志里有 `spawn` 行就回送原来的结果，不再发起；目标或入参不同按对不上处理。新树的 root 行先落盘，发起方的 `spawn` 行后落盘：两行之间崩溃时，发起方的日志里没有这一步，重新执行到这一步时，发起的目标与入参相同就接回那棵已恢复的树（补发 `run.spawned`、记 `spawn` 行），不再起一棵；不同就照常另起，旧的那棵自己跑完。
  - 新树的根没有 `ctx.callerPackage`（它是根）。
  - 解释器里 `ctx.spawn` 与 `ctx.call` 经同一个宿主函数，`harness_exec` 的 100 次上限两者一起算。终端客户端把 spawn 起的根画成 `⇢ 名字 入参（另起一棵树）`，缩进接着发起方；它与发起方各跑各的，结束那行常夹在别的 Run 下面，带「（另起的树）」。
- **原因**：后台的事（评测打分、整理记忆、审计）不该拖住前台的调用，也不该把结果塞回调用方；方案的处理器、评测、budget 的归账都建在它上面。真模型试过：让它经 `harness_exec` 跑一段 `ctx.spawn("fs_list", …)` 的脚本，脚本拿到新树的 runId 就返回，`fs_list` 在另一棵树里跑完，日志随之删掉。
- **影响**：
  - MVP 里还没有用它的包；`harness_exec` 的用法说明没提它，模型现在不会用。
  - 还没有 budget：`spawn` 的次数只受保险丝（深度、同时存活的 Run 数）管。
- **代码**：`stdlib/kernel/kernel.ts`（spawnTree、replayed、gate、admit 的 place、recover 的 orphans、execute 的 started）、`run.ts`（Ctx.spawn、Run.spawnedBy）、`ops.ts`（Spawn）、`events.ts`（run.spawned，run.started 与 call.rejected 的新字段）、`journal.ts`（spawn 行、root 行的新字段、新树结束即删）、`replay.ts`、`chain.ts`（每个装饰器一份 ctx）、`plugin.ts`（afterRunSpawn）、`stdlib/script/`（ctx.spawn）；`client/console/tree.ts`。测试 `stdlib/kernel/spawn.test.ts`、`stdlib/plugins/harness/exec.test.ts`、`client/console/tree.test.ts`。

| 日志的内容 | 一棵树一个 JSON Lines 文件，以根 runId 命名。七种行：`root`（根与外部给的原始入参、产物摘要、谁发起的；spawn 起的树还有发起方、第几步、深度、不装载哪些包的装饰器）、`call`（发起的调用：序号、目标、入参摘要、子 Run 的 runId）、`spawn`（发起的 spawn：序号、目标、入参摘要、结果，发起即完成，见一.21）、`done`（第几个调用完成与结果，同一个 Run 的 done 行先后即完成顺序）、`park`（第几步的 park 关闭时的产出）、`retry`（恢复时重新执行了哪个 Run、第几次）、`exit`（最后一行：根结束了，结果与结束的时刻，留到被取走）。一个 Run 的调用、spawn 与 park 共用一套序号，实现与装饰器的也一起编号；在内核就被拒的调用也记。每行都由事件推出：`run.started` → 根的 `root` 行、子 Run 的父的 `call` 行、重新执行的 `retry` 行；`run.spawned` → 发起方的 `spawn` 行；`call.rejected` → `call` 与 `done` 行（spawn 被拒是 `spawn` 行）；`run.exited` / `run.killed` → 父的 `done` 行，根的 `exit` 行；`park.closed` → `park` 行；`run.reaped` → 删日志 | `journal.ts`（commit） |
| 写入 | 在提交阶段同步写并 fsync，落盘后事件才交给订阅者与插件、内核才往下走：调用落盘后才执行，结果落盘后才交给父，park 的值落盘后才送进去。子 Run 的入参不记：恢复时父会再发起同样的调用 | `events.ts`（emit）、`journal.ts`（commit） |
| 写盘失败 | 提交阶段抛的异常从转换点往外抛，这次转换做到一半；按崩溃处理：进程应退出，重启后从已落盘的部分恢复。后续：明确的 fail-stop | `events.ts`（emit） |
| 何时删、何时不记 | 按根的 `run.exited` / `run.killed` 处置：正常结束、被取消时记 `exit` 行，结果取走（`run.reaped`）才删，spawn 起的树没人取，直接删；关停保留；别的原因（比对不上、恢复时根建不起来）移到 `diverged/` 下留着排查，不再恢复。Run 已结束或被杀后它的事件不再记（日志只跟踪在途的 Run）：关停时日志停在被杀之前，重启后接着跑 | `journal.ts`（commit、end） |
| 恢复的入口 | `kernel.boot()`：插件都 `onStart` 过之后、`afterStart` 之前恢复，返回各树根的 runId 供收割，已结束、结果还没被取走的也在内，spawn 起的不在内；入口经 `outside.recovered()` 认领自己发起的那些。`submit` 必须在 `boot` 之后，否则 `boot` 之前起的树会在恢复时再执行一遍。崩溃时写了一半的末行截掉。根都建不起来（Operation 没了、入参不再合法）时恢复失败 | `kernel.ts`（boot、recover）、`journal.ts`（readAll、fold） |
| 重放 | 重新执行的 Run 按序号回放：调用比对目标与入参摘要，已完成的回送记下的结果（不执行、不过链、不发事件），在途的子 Run 用原 runId 重新执行；park 已关闭的直接拿产出，没关闭的用原 id 重新开出（照常发 `park.opened`）。越过记录末尾后照常执行 | `kernel.ts`（callChild、park） |
| 回送的顺序 | 已完成的结果按崩溃前的完成顺序（同一个 Run 的 done 行与 park 行的先后）逐个交还，每交还一个先让代码跑一步，并发发出的调用拿到结果的先后与原来一致。在途重新执行的与越过末尾的新调用不参与排序 | `replay.ts` |
| 比对不上 | 只看代码看过结果的那些步：已完成的那一步对不上（目标、入参不同，或调用与 park 互换），或 Run 结束时还有已完成的记录没走到（`got exit`），判为对不上。整棵树按 killed 处理，原因写明哪一步（`diverged at #序号 of Operation: journal has …, got …`），park 作废，日志移到 `diverged/` | `kernel.ts`（diverge、callChild、park、settle） |
| 产物摘要 | Operation 与装饰器的声明及代码（impl / fn 的源码文本）、默认装饰器集，取 sha256，写进日志的根行。方案是「不一致不恢复」；实现只在 `tree.recovered` 里提示（`artifactChanged`），照常恢复，靠逐个调用比对兜底，升级代码时停在 park 上的任务不至于全部作废 | `kernel.ts`（artifact） |
| 恢复事件 | 每棵恢复的树发一条 `tree.recovered`：根的 Operation 与谁发起的（`origin`）、日志里已完成的调用与 park（带结果，重放时不再发事件，崩溃前没来得及发的 `run.exited` / `park.closed` 据此补齐）、要重新执行的 Run、产物是否变了。根建不起来时再发 `run.killed`，原因即收割到的拒绝原因；比对不上的同样是 `run.killed`（diverged …） | `kernel.ts`（recover）、`events.ts` |
| 事件的启动 id | 每条事件带 `boot`（UUIDv7，按时间有序），重启后 `seq` 从头数，下游按「boot + seq」排序。启动不发事件：换了 boot 即重启过，插件经 `onStart` / `afterStart` 得知 | `events.ts` |
| 事件里给日志用的字段 | `step`：`run.started` 是它在父里（spawn 起的根：在发起方里）的第几步，`call.rejected` 是发起方的第几步，`park.closed` 是这个 Run 的第几步，即日志行的 `seq`，事件与日志一一对上（原名 `callSeq`）。`run.started` 的 `input` 是调用方给的原样入参（实现拿到的是按 schema 解析后的），日志的入参摘要与恢复时的比对都用它；根 Run 的 `run.started` 带 `artifact`（产物摘要），经服务接口发起的还带 `origin`（谁发起的） | `events.ts`、`kernel.ts`（execute、callChild、closePark） |
| 在途的那一步换路 | 崩溃时在途的那一步，结果从没交给过代码：重新执行时改发别的调用或改成 park（比如 `attempt > 1` 时先查重）不算对不上。旧的在途调用作废、不再执行，新调用照常执行并记一行覆盖旧的；没走到的只剩在途的，也作废 | `kernel.ts`（callChild、park） |
| `attempt` | 恢复时重新执行的 Run（包括根）在上次的基础上加一，先记一行 `retry`，再崩一次还能接着加；`run.started` 在大于 1 时带上它 | `kernel.ts`（resume） |
| 不确定的值 | 经 Operation 取（`time_now`；以后 random、uuid），不直接用 `Date.now()`：结果随调用记进日志，重放时回送当初的值。调用结果要能 JSON 序列化 | `stdlib/plugins/time/index.ts` |
| 关停的两种模式 | `stop(timeoutMs)` 优雅关停：不接新的外部调用，树里新发起的调用与 park 停在边界上（不执行、不记日志）；等正在执行的调用跑完，没有正在执行的了（只剩停住的与 park）就把在途的树按 shutdown 杀掉，到超时则转强杀。`stop(0)` 强杀，什么也不等。日志都保留：优雅关停停在干净的边界上，重启后没有执行到一半的调用；强杀等同崩溃，在途的重新执行、attempt 加一。方案是「等在途的树收敛或超时」，树要跑很多轮或在等 park 时几乎总会拖到超时 | `kernel.ts`（stop、hold、checkQuiet） |
| 内核的生命周期 | 装配中（`use`、`register`）→ 启动中（排先后、查装饰器引用、插件 `onStart`）→ 运行中（接受调用）→ 关停中。`use` 只能在 `boot` 之前；`boot` 只能一次；`stop` 要在 `boot` 之后，重复调用（比如优雅关停中又强杀）时插件的 `onStop` 只跑一次。启动失败停在启动中，不再接受调用；已 `onStart` 的插件不回滚。`register` / `registerDecorator` 是底层接口，不受阶段限制 | `kernel.ts`（use、boot、stop） |
| 能拦的挂点 | 按这个挂点排好的先后问（见一.12 的 `order`），第一个拦下的生效，后面的不再问；拒绝结果的 `by` 是拦下的插件的包名。必须同步（转换是同步的，等不了；要做 IO 的策略用装饰器），写成 async 类型检查报错，运行时返回 Promise 按拦下处理；抛异常也按拦下处理（管控出错必须中断）并记下。在提交阶段之前：被拦下的结果照常进事件与日志（子调用是 `call.rejected`，退出是 `run.exited`，park 是没有 `park.opened` 的 `park.closed`，树是 `run.killed`），恢复重放时原样回送，不再问挂点；被拦下的外部调用与 `unpark` 只抛异常，什么也不记 | `plugin.ts`（BEFORE）、`kernel.ts`（before） |
| 通知类挂点的先后 | 一条事件先按它的 `after*` 挂点排好的先后调，再按 `afterAny` 排好的先后调 | `kernel.ts`（dispatch） |
| 装饰器引用的检查 | 启动时就查：默认装饰器与各 Operation 的自选装饰器都得注册了；插件的 Operation 引用别的包的装饰器（如 `fs_write` 用 `ui_approval`），那个包须在它的 `requires` 里。启动之后才注册的 Operation 仍在调用时查 | `kernel.ts`（checkDecorators、admit） |
| 挂点出错 | `after*`、`afterAny`、`afterStart` 不等它返回，出错（同步抛出或 async 拒绝）只记下，带上插件与方法名，不影响执行与其他插件；`onStart` 出错启动失败；`onStop` 出错只记下、继续关停 | `kernel.ts`（use、boot、stopPlugins）、`events.ts`（notify） |
| 插件的配置 | 装载器把配置原样交给工厂，缺省 `{}`，目前不校验；以后按插件声明的 schema 校验 | `loader.ts` |
| 事件流的订阅者 | `kernel.events.subscribe` 留给宿主、服务接口（事件流）与测试，与 `afterAny` 同语义；Harness 外面的客户端经服务接口的 `/events` 看事件 | `events.ts` |
| 内容块与图片 | 插件之间约定的形状在 `stdlib/content.ts`：内容块 `ContentBlock`（文字，或图片：base64 与类型，与 pi-ai 的同形）；工具结果带图片时是 `ToolContent`（`{ content }`，只有文字的直接是字符串），调模型的一方原样放进工具结果；用户发来的图片按 `image` 校验（png、jpeg、gif、webp，base64）。内核不解释它们。图片的 base64 会随调用结果进写前日志、事件与对话历史，还没有大小上限 | `stdlib/content.ts` |
| `ctx.ops` 的运行时 | Proxy：`ctx.ops.包.键(入参)` 转成 `ctx.call("包_键", 入参)`；不认 `then`，免得 `await ctx.ops.fs` 之类把它当成 thenable。装饰器的 `ctx` 也有 | `ops.ts`（calls） |
| `ctx.park` 的约束 | 同一个 Run 同时只能 park 一次；Run 被杀后还在跑的代码调它抛异常；实现没等 park 就返回时，Run 等 park 关闭后才退出（与没 await 的子调用一样） | `kernel.ts`（park、settle） |

## 三、MVP 期间的临时做法

之后要回到方案，或另行决定。`stdlib/` 是框架包，放内核、宿主、服务接口与正式的插件；`app/mvp/` 下的 script 包（agent、chat）、装配配置与终端客户端的配置只用来验证内核、演示怎么搭一个 harness，正式实现不用。`fs`、`model` 插件已移进 stdlib（见一.13），下面记的仍是它们现在的临时做法。

| 终端对话 | UI 渲染对话（3.5） | 终端客户端（`client/console`，在 Harness 外面，经 HTTP 服务接口）：普通一行交给配置的 `say`（入参 `{ text }`），「/命令」调配置的命令（入参 `{}`），`/exit`、输入结束或 Ctrl-C 退出；连上时开场调 `greet`，再接着等自己（origin `http:console`）上次发起、还没取走结果的树；返回的文字显示出来，失败显示 `失败（谁）：原因`。问题来自事件流里新开的，加上连上时已经在等的（`GET /parks`）；一份按行读的输入由对话与回答问题共用，排队读，不抢同一行；问题在开场之后才问。事件流按 Run 树缩进画出来，各 Operation 的摘要规则由应用给（`app/mvp/client/brief.ts`）。回答在这一轮的 Run 树画完之后才显示：结果经 HTTP 返回，可能比事件流里最后几条先到，客户端先等根 Run 的结束事件（最多一秒）。回答里的 Markdown 换成终端的写法（`client/console/markdown.ts`：标题与加粗为粗体，代码青色，引用前加竖线，去掉代码块围栏；输出不是终端时只去掉标记），渲染归客户端，别的客户端（如网页）可以原样渲染。退出只是客户端走了：在途的那一轮在 Harness 里照常跑，结果留着，问题照旧等着，下次连上接着显示；Harness 停下时客户端也退出，那一轮算没做完：关停的结果、调用的连接断开、事件流断开谁先到都算，先到的说一声「Harness 断开了」；服务接口回的错误（如没对外）才算这一轮失败。MVP（`app/mvp/client/main.ts`）配成 `say: chat_say`、`/new` → `chat_reset`、`greet: chat_greet`。命令：`bun run serve` 起 Harness，`bun run chat ["第一句"]` 开终端，`bun start ["第一句"]` 两个一起起（Harness 已在跑就只开终端）。对话由 script 包 `chat`（`app/mvp/server/scripts/chat`）管：`chat_say` 依次调 `kv_get`、`agent_assist`、`kv_set`，历史存在 kv 里 chat 的键 `conversation`（`STATE_DIR/store/kv/chat/conversation.json`，整个替换），失败的一轮不存。存是 Run 里的子调用，存完根 Run 才退出、日志才删，原来「日志先删、对话后写」的缺口没有了。同一时间只该有一轮，两轮同时会争同一份历史 |
| 停下与接着做 | 关停时投递插件 flush、编排方对账（9.2、9.4）；关掉沙箱再起来能接着答问题（P3 验收） | 宿主：Ctrl-C 或 SIGTERM 优雅关停（服务接口先停止接新连接，等在途调用最多 10 秒），再来一次强杀，进度都留在日志里；进程被杀也一样。`bun start` 起的 Harness 在另一个进程组里，终端退出时（Ctrl-C、`/exit`，`start.ts` 被 SIGTERM 或终端关掉的 SIGHUP 也一样）由 `start.ts` 发 SIGTERM 让它优雅关停，关停中再按 Ctrl-C 强杀；还有一轮没做完时提示「已停下，进度已保存」。再运行 `bun start`，Harness 接着做没做完的树，终端客户端开场后显示「接着等上次没做完的 chat_say…」并等它的结果，停着的问题用原 id 再问一次。只开终端（`bun run chat`）时退出不影响 Harness，提示「已断开」。不想接着做就删掉 `STATE_DIR/journal` |
| 观测 | 投递插件订阅事件、送往观测平台（9.2） | 还没有投递插件。终端客户端经服务接口的事件流（`/events`）按 Run 树缩进画出来，日志（`run.logged`）画在它的 Run 下面；各 Operation 的入参、出参怎么摘要由应用给（`app/mvp/client/brief.ts`），对不上时退回截断的 JSON。客户端连上之前的事件看不到 |
