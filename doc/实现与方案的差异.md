# 实现与方案的差异

对照 `harness-技术方案.md`（下称「方案」），记录实现里与方案不一致、或方案没写而实现自定的地方。方案本身暂不改；实现有变化时同步更新本文件。

---

## 一、已定的设计改动

### 1. 命名：`包名_键名`

- **方案**：Operation 名为 `包名.函数名`，如 `fs.read`（1.3、6.1、7.3、附 A）。
- **实现**：`包名_键名`，如 `fs_read`。键名是它在插件对象 `operations` / `decorators` 里的键（见 12）。包名只含小写字母、数字与 `-`；键名只含字母与数字；整名最长 64。名字里恰好一个 `_`，就是分隔符。装上插件（`kernel.use`）时校验包名与整名。
- **原因**：模型的工具名只接受字母、数字、`_` 与 `-`。这样 Operation 名原样就是工具名，事件、模型历史、日志里处处同名，便于追踪，也不需要任何转写。
- **代码**：`stdlib/kernel/names.ts`、`kernel.ts`（use、register）。

### 2. Operation 的声明：`op()` / `decorator()`，入参用 Zod

- **方案**：导出函数即 Operation，JSDoc 正文是 `usage`，标签写 `@public`、`@decorators`、`@only` 等；d.ts 与 JSON Schema 由同一个工具在构建期从 TS 类型生成（6.1、7.3、R4、R19）。
- **实现**：插件对象的 `operations` / `decorators` 里放 `op({ input, usage, public, decorators, only, exclude, impl })` 或 `decorator({ onError, fn })` 的声明（插件对象见 12）。入参是 Zod schema：TS 类型由它推出，运行时按它校验，交给模型的 JSON Schema 在注册时由 `z.toJSONSchema` 生成。
- **原因**：一处定义同时得到类型、schema 与校验；不需要构建步骤，也不用解析注释。
- **影响**：`usage` 从 JSDoc 挪到字段；以后 script 包要在 QuickJS 里带上 Zod，解析开销待实测。
- **代码**：`stdlib/kernel/plugin.ts`、`kernel.ts`（use）。

### 3. 当前 Run 经显式的 `ctx` 传递

- **方案**：用 AsyncLocalStorage 绑定当前 Run，Operation 恰好一个入参；插件之间 `import { read } from "fs"`，打包时换成按名字的调用（6.2、3.1、R4）。
- **实现**：`ctx` 作为第一个参数：实现是 `impl(ctx, input)`，装饰器是 `fn(ctx, run, next)`。调别的 Operation 写 `ctx.ops.fs.read(input)`，名字是变量时写 `ctx.call(name, input)`（类型见 14），返回结果对象（`{ ok, value }` 或拒绝），而不是值本身。
- **原因**：没有隐式上下文，插件可以传假 `ctx` 单测，也没有「上下文丢失」这条残余风险（方案 10.8、附 C）。
- **代码**：`stdlib/kernel/run.ts`（Ctx）、`kernel.ts`（execute）。

### 4. 装饰器 id 不自定义

- **方案**：`@decorator <id>` 声明注册名（5.2）。
- **实现**：装饰器 id 与 Operation 同一套命名，就是 `包名_键名`。
- **代码**：`stdlib/kernel/kernel.ts`（use）。

### 5. 取消用 `ctx.signal`，不设 `run.cancelling` 责任链

- **方案**：取消「走 `run.cancelling` 后转 killed」，由插件在生命周期责任链上收尾（5.1、附 A）。
- **实现**：每个 Run 带一个 AbortController，`ctx.signal` 在 Run 被杀（取消或关停）时 abort。原语把它传给 fetch、子进程等，IO 当场中止。没有 `run.cancelling`。
- **原因**：比责任链简单，是 JS 的惯用法；内核不用等插件收尾，取消不会被拖慢。
- **代码**：`stdlib/kernel/kernel.ts`（kill）、`run.ts`（Ctx.signal）。

### 6. 装饰器的 `ctx` 上没有 `tools()`

- **方案**：调用方是装饰器时，交给模型的工具缺省为空（8.1）。
- **实现**：更严格：装饰器的 `ctx` 类型是 `Omit<Ctx, "tools">`，装饰器里写 `ctx.tools()` 直接编译不过。
- **代码**：`stdlib/kernel/chain.ts`（DecoratorCtx）。

### 7. 交给模型的工具由调用方显式传入

- **方案**：`model.complete` 的 `tools` 缺省为调用方能力面里公开的 Operation，不含 `model` 包自身（8.1）。
- **实现**：调用方用 `ctx.tools()` 取得工具列表，再作为入参传给 `model_complete`；`model_complete` 本身不公开，所以不会出现在工具列表里。
- **原因**：`model_complete` 保持为纯原语，工具列表只是数据；调用方传常量列表，前缀更好控制。
- **代码**：`stdlib/kernel/kernel.ts`（toolsIn）、`app/mvp/plugins/model/index.ts`。

### 8. 放行不发事件

- **方案**：装饰器链每一环的处置都进事件流（3.7-4、9.1）。
- **实现**：链序记在 `run.started.chain` 里；放行不发事件，只有改写、拒绝、出错各发一条（`decorator.rewrote` / `decorator.rejected` / `decorator.failed`）。
- **原因**：少发大量「什么都没做」的事件；链序加上这三类事件，足以还原每一环做了什么。
- **代码**：`stdlib/kernel/chain.ts`。

### 9. `running` ↔ `waiting` 不发事件；能力面不写进事件

- **方案**：每个状态转换点都发事件（9.1）；复盘靠「Run 建立时的能力面」（9.6）。
- **实现**：父 Run 何时在等，可由子 Run 的 `run.started` / `run.exited` 推出，不单独发事件。能力面由 Operation 的声明静态决定，看 operation 名加产物版本即可还原，不在每个 `run.started` 里重复。

### 10. 内核不注册 Operation；park 的 Operation 在 stdlib 的 harness 插件里

- **方案**：`harness.park`、`harness.exec` 是内核提供的 Operation（3.5、附 A「`harness` 包」）；`harness.park` 是唯一不靠子 Run 而进入 `waiting` 的 Run（3.4）。
- **实现**：内核只提供机制：实现的 `ctx.park({ schema, payload })` 让当前 Run 转 `waiting`，对外接口 `unpark` / `withdraw` 送值或撤回。Operation 形式 `harness_park` 在 stdlib 自带的 harness 插件里（`stdlib/plugins/harness`），装配时按需装载。装饰器的 `ctx` 没有 `park()`：装饰器要挂起就 `ctx.call("harness_park", …)`，好让外层装饰器（如无人值守的短路）看得到。
- **原因**：注册表里的 Operation 全部来自装载的插件，内核不带原语。
- **影响**：原生插件的实现可以直接 `ctx.park` 挂起自己的 Run，不经 park Operation，装饰器看不到这次挂起（原生插件本就是受信的内侧代码）。
- **代码**：`stdlib/kernel/kernel.ts`（park、unpark、withdraw）、`run.ts`（Ctx.park）、`chain.ts`（DecoratorCtx）、`stdlib/plugins/harness/index.ts`。

### 11. 恢复靠写前日志，没结束的树都能恢复

- **方案**：树空闲时写快照、活跃前删，只恢复空闲的树；任意步续跑交给工作流引擎（3.6、11.4、R11、R29）；装配配置 `snapshotDir`。
- **实现**：每棵树一个只追加的日志，放在内核专属目录（装配配置 `journalDir`）。日志是事件流的持久投影：每条事件先过提交阶段，由它推出日志行同步落盘，再交给订阅者与插件，内核才往下走；插件看不到这一步，也拦不了。调用发起、调用完成、park 关闭，都这样先落盘再继续；树结束或被取消时删，关停时保留。启动（`kernel.boot()`）时重建所有没结束的树：已完成的调用回放；崩溃时正在执行的 Run 用原 runId 重新执行，并经 `ctx.attempt` 告诉它这是第几次执行。要落日志、要恢复的东西一律经 Operation 取：时间这类不确定的值调 `time_now`，状态将来是 state 插件的 Operation（存储由插件自己管）；调用结果本就记进日志、重放时回送，内核不另设接口。
- **原因**：崩溃时正在执行的原语（比如发邮件）有没有生效，只有它自己知道。内核给出信号和稳定的 runId（可当幂等键），由原语决定查重、跳过还是重做，与 Temporal 的 attempt、Stripe 的 Idempotency-Key 同理。
- **影响**：每次调用多两次同步写盘；写原语要考虑 `attempt > 1`，不处理时语义是「至少执行一次」；日志随树增长，长期存在的树以后要压缩。内核仍不做重试策略与补偿。
- **代码**：`stdlib/kernel/journal.ts`（commit）、`events.ts`（EventStream 的提交阶段）、`kernel.ts`（recover、callChild、park）。

### 12. 插件是工厂函数；生命周期与事件挂点是插件对象上的方法

- **方案**：插件包导出函数即 Operation，`setup(config)` 拿配置（6.1、附 A）；插件经 `@on` 处理器订阅事件；启动、关停各有 `harness.started`、`harness.stopping` 责任链（9.2）。
- **实现**：插件包默认导出 `plugin((config) => 插件对象)`。装载时以装配配置调一次工厂，工厂里的变量就是这个插件实例自己的状态（一个内核一份），工厂本身也就是 `setup(config)`。插件对象里放：
  - `requires`：依赖的插件。缺了启动失败；插件按依赖拓扑排序（同级按装载顺序），有环启动失败。只做检查与排序，不自动装载：装什么仍由装配侧决定；
  - `order`：按事件挂点调整先后，如 `{ beforeRunStart: { before: ["ui"] } }` 把自己在这个挂点上排到 ui 前面。事件挂点缺省依赖（含间接的）在前；`before` 里的排在自己之后，`after` 里的排在自己之前；没装的插件忽略，排出环启动失败。`onStart` / `onStop` 不能调：依赖必须先启动、后关停；
  - `operations`、`decorators`：声明（见 2），名字取 `包名_键名`；
  - `onStart()`：启动时（`kernel.boot()`）按依赖的先后逐个 await，抛异常则启动失败；之后才恢复没结束的树、开始接受调用；
  - `afterStart()`：启动完成后（树已恢复）通知；
  - `onStop()`：关停时，在途的树杀掉之后，按依赖的逆序逐个 await（依赖后关）；
  - `after*(event)`：每种事件恰好对应一个方法（`afterRunStart`、`afterRunExit`、`afterRunKill`、`afterCallReject`、`afterParkOpen`、`afterParkClose`、`afterTreeRecover`，三种装饰器事件合为 `afterDecorate`），只读通知；
  - `afterAny(event)`：所有事件，投递、观测类插件用；
  - `before*(event)`：能拦的挂点，转换发生之前同步调，拿到将要发出的事件，返回 `{ veto: 原因 }` 即拦下：`beforeRunStart`（子调用以拒绝返回、不建子 Run；外部调用抛异常）、`beforeRunExit`（结果换成拒绝）、`beforeParkOpen`（不等待，park 直接以拒绝关闭）、`beforeParkClose`（外部送值或撤回抛异常，park 照旧等待）、`beforeTreeRecover`（这棵树不恢复）。

  没实现的方法不调。插件对象里有不认得的键（比如挂点方法名拼错）时装载即报错。
- **原因**：游戏引擎式的脚本挂点：插件想接哪个时机就实现哪个方法，一个对象就是插件的全部；工厂给每个内核实例一份独立的状态，配置不再走全局的环境变量。装饰器保留：它在 Run 里面、可回放、包住一次调用（审批的 park、计时、预算的预留与结算）、按 Operation 自选并有顺序；挂点是 Run 外面的全局时机。
- **影响**：方案 R14 要求全局行为由装配侧决定，插件不能因为注册了什么就改变全局行为。`before*` 能拦所有调用，是全局的；这里由装配侧决定装不装这个插件来体现。只有原生插件有挂点，script 包没有。
- **代码**：`stdlib/kernel/plugin.ts`（plugin、AFTER、BEFORE、PluginObject）、`kernel.ts`（use、boot、arrange、stop、before、dispatch）、`order.ts`（topo）、`loader.ts`。

### 13. 代码组织：`stdlib` 框架包与 `app`

- **方案**：插件与 script 包从 `harness` 包 import 运行时函数（`call`、`emit`、`spawn`）与内核的 Operation（`harness.park`、`harness.exec`）（3.1、附 A「`harness` 包」）；别的包 `import { read } from "fs"`。
- **实现**：
  - `stdlib/` 是框架包，import 名就是 `stdlib`（`tsconfig.json` 的 `paths`，Bun 运行时同样认）。`stdlib/index.ts` 是唯一的公开入口：写插件用的 `op` / `decorator` / `plugin` 与 `Ctx`、`Result` 等类型，搭应用用的宿主 `host` 与装配配置 `Assembly`（见 15）；`Kernel`、`loadPlugin` 给测试与自己搭宿主用。内核在 `stdlib/kernel/` 下，其余模块（日志、回放、入口的声明 `entry` 等）不导出。
  - stdlib 自带的插件在 `stdlib/plugins/` 下，按领域分包：`harness`（`harness_park`，即方案的 `harness.park`；以后放 `harness_exec`）、`time`（`time_now`）、`ui`（给人看的问题的约定格式与审批，见三）。基建的接口与实现在 `stdlib/infra/` 下（见 16）；服务接口在 `stdlib/serve/` 下：`http`，由宿主按装配配置 `serve` 启停（见 15）；入口在 `stdlib/entries/` 下：`console`（终端，过渡，下一步改成客户端）。装配配置里按路径写，如 `"stdlib/plugins/time"`。
  - `app/` 下是用 stdlib 搭出来的 harness 实现，各自带装配配置与自己的插件；`app/mvp` 演示怎么搭，`main.ts` 只有装配配置。
  - 每个应用一份 `tsconfig.json`（继承根配置），只编译这个应用，它的装配类型不影响 stdlib 与别的应用（见 14）。
  - 运行时函数在 `ctx` 上（见 3），不从包里 import。
- **原因**：框架与应用分开，应用怎么搭一目了然；import 不再写一串 `../`。
- **代码**：`stdlib/index.ts`、`tsconfig.json`、`stdlib/plugins/`、`stdlib/serve/`、`stdlib/entries/`、`stdlib/host.ts`、`app/mvp/main.ts`。

### 14. 调用的类型从插件源码推出，由应用登记

- **方案**：包的 d.ts 由同一个工具在构建期从 TS 类型生成（7.3、R19）；插件之间 `import { read } from "fs"`，打包时换成按名字的调用（3.1、6.2）。
- **实现**：
  - `op()` 记下入参的类型（`z.input`，即调用方要填的形状，带默认值的字段可不填）与出参的类型（实现的返回值），`plugin()` 记下插件对象的具体类型。
  - 用 `import type` 把包登记进 `Packages`（`declare module "stdlib"`）：stdlib 自带的由 stdlib 登记（`stdlib/plugins/packages.ts`，`stdlib/index.ts` 以三斜线引用），用 stdlib 的都有这些类型；应用只登记自己的插件（`app/mvp/packages.ts`）。不手写 d.ts，运行时什么也不加载。
  - 插件里写 `ctx.ops.fs.read({ path })`：包或 Operation 不在注册表里、入参不对，编译即报错；结果带类型，编辑器能补全。
  - `ctx.call(name, input)`：名字在注册表里时同样带类型；名字是变量（模型挑的工具）或不在注册表里（测试里临时注册的）时，入参与结果是 `unknown`，不报错。
  - 运行时 `ctx.ops.fs.read(x)` 就是 `ctx.call("fs_read", x)`，照常过装饰器、能力面、日志与事件，事件与日志里的名字不变。
- **原因**：类型与实现同源，不会对不上；不需要构建步骤；显式 `ctx` 下也能像调包里的函数一样读写。
- **影响**：
  - 类型只是契约：不知道能力面，也不知道这次装没装，这两样仍由运行时拒绝。
  - 装饰器改写的结果不反映在类型上（如 `ui_approval` 带说明时把结果包成 `{ result, userNote }`）。
  - 插件的出参若由调用自己包里 Operation 的结果推出，类型会绕成环，要给 `impl` 标返回类型。
  - `ctx.call` 不补全名字、拼错不报错：它只查名字里的那个包，查全表会把调用方自己的包卷进来、绕成环。写死的调用用 `ctx.ops`。
  - 装配类型文件要与入口装载的插件保持一致，以后由装配配置生成；给 script 包（QuickJS）的 d.ts 也可以从这份注册表生成。
- **代码**：`stdlib/kernel/ops.ts`、`plugin.ts`（op、plugin）、`run.ts`（Ctx、Result）、`stdlib/plugins/packages.ts`、`app/mvp/packages.ts`、`app/mvp/tsconfig.json`；类型检查 `app/mvp/packages.check.ts`。

### 15. 宿主与服务接口：对外接口只交给服务接口，启停只归宿主

- **方案**：Harness 的对外接口（调用、`unpark` / `withdraw`、取消、收割）由外部使用，外侧只能调公开表里的 Operation（1.4、7.2、附 A）；没说由谁在进程里把外面的请求接进来，也没说进程由谁启停。
- **实现**：
  - **宿主**（`stdlib/host.ts`）：一个进程一个 Harness，只有它握着内核。`host(装配配置)` 先占住服务接口要监听的地址（被占了即同一个状态目录已有 Harness 在跑，不往下启动、不碰日志），再建内核、按顺序装载插件、启动（恢复上次的树），然后让服务接口开始监听。收到 SIGINT / SIGTERM 就优雅关停：服务接口先停止接新连接，内核等在途的调用跑完（最多 `graceMs`，缺省 10 秒），关停中再收到一次就强杀；内核关停完断开连接、退出进程。启停是机器的信号，插件碰不到。
  - **服务接口**（`stdlib/serve/`）：Harness 对外提供服务的协议层，由装配配置的 `serve` 决定开哪些、监听在哪、对外哪些 Operation（`expose`），与 `plugins`（能力）分开：前者跟着部署走，后者跟着应用走。看装配配置就知道对外了什么；不在 `expose` 里的一律当作没有。现在有 HTTP（见二的「HTTP 服务接口」）；以后 gRPC 等也加在这里。只在 stdlib 里写，对外接口只交给它们。
  - **对外接口 `outside`**（`stdlib/kernel/outside.ts`）：`submit`（只能调声明了 `api` 的 Operation）、`wait`（等结束，不取走）、`reap`（取走结果）、`runs`（结果还没被取走的树）、`parks`（等待中的问题）、`unpark`、`withdraw`、`operations`（对外的 Operation 与入参 JSON Schema）。经它发起的树，根记下 `origin`（谁发起的；HTTP 是 `http` 或 `http:客户端自报的名字`），进 `run.started`、日志的根行与 `tree.recovered`，重启后还在。
  - **根的结果留到被取走**：调用方可能不在（断开、关了 UI、中途重启），所以根 Run 结束时结果写进日志（`exit` 行），取走（`reap`）才删；关停时被杀的树不算结束，重启后接着做；没人取的放 `resultTtlMs`（缺省 7 天）后在启动时清掉。见二的「收割」。
  - **`api` 与 `expose`**：插件给自己的 Operation 声明 `api: true`，表示它适合对外（比如 `chat_save` 会覆盖整份历史，就不该声明）；对不对外由装配配置里各服务接口的 `expose` 决定，只能列 `api` 的：写在 `main.ts` 里，名字由注册表推出（`ApiName`），拼错或不是 `api` 的类型检查即报错，启动前再查一遍，不对就启动失败。`api` 与 `public` 分开：`public` 是交给模型当工具，`api` 是能对外，比如 `chat_say` 对外而不给模型，`fs_write` 给模型而不对外——方案的公开表在这里分成两张。
  - **对外的契约**：`api` 的 Operation 必须写 `usage` 与出参 schema `output`，注册时检查；入参与出参都须能转成 JSON Schema，由 `GET /operations` 给出。写了 `output` 的 Operation（不限于 `api`）返回前按它校验：对不上算它自己失败（`invalid output`），对得上交出解析后的值。
  - 宿主与测试直接调内核：`kernel.submit`（原名 `start`，免得与开机混淆）什么都能调，不记 `origin`。
  - **过渡**：终端还是入口（`stdlib/entries/console`，用 `entry()` 声明的特殊插件，工厂多拿一份 `outside`，`serve()` 结束即关停）。下一步改成连 HTTP 服务接口的客户端，届时去掉 `entry()` 与入口。
- **原因**：应用的逻辑都写成插件，`app/mvp/main.ts` 只剩装配配置。插件的权限就是 stdlib 给的那些：Run 里的 `ctx`、事件挂点、给自己的 Operation 声明 `api`；能从外面发起调用、回答问题的只有 stdlib 的服务接口；进程启停只在宿主。插件写完、声明 `api`，就是一个 API。UI（终端、网页）与别的系统都是客户端，走同一套服务接口。
- **影响**：
  - 原生插件与内核在同一个进程里，技术上能 import 任何东西；这里约束的是 harness 层面的权限，代码层面靠 review 与 lint（6.4），真正不可信的代码走 script 包。
  - 新协议只能加在 stdlib 里，应用不能自带。
  - 还没有认证：Unix socket 靠文件权限（只给本用户），TCP 缺省只绑 127.0.0.1，不要对外开放；`runs`、`parks`、事件流对所有调用方都是全量的，有了认证再按调用方过滤。
  - 只有开了 Unix socket 时才能挡住同一个状态目录上的第二个 Harness；写前日志本身还没有锁。
  - 后续：自举用的 `harness_restart`——这次调用先完成、写进日志，宿主再以约定的退出码退出，由外层重新拉起，调它的树用新代码接着做；没先写进日志的话，恢复时会再调一次，无限重启。
- **代码**：`stdlib/host.ts`、`stdlib/serve/`、`stdlib/kernel/outside.ts`、`kernel.ts`（submit、outside、wait、reap、runs、parks、recover）、`journal.ts`（exit 行、run.reaped）；过渡中的 `stdlib/kernel/entry.ts`、`loader.ts`、`stdlib/entries/console/`。测试 `stdlib/host.test.ts`、`stdlib/serve/http.test.ts`、`stdlib/kernel/outside.test.ts`。

### 16. 四层与基建：插件不直接做 IO，基建由装配提供、宿主注入

- **方案**：插件在 `setup` 里 `provides` / `require` 服务，服务名描述能干什么（`model-backend`、`store`、`isolate`），按消费方创建、隔离由提供方负责（6.3、6.4、R17、附 A「服务名」）；没有把整体分层写出来。
- **实现**：装配配置按四层写（`app/mvp/main.ts`）：
  - **接口**（`serve`）：哪些 Operation 怎么对外（见 15）。
  - **应用**：编排，比如 agent 循环、对话（`agent`、`chat`）。以后是 script 包；现在还写成插件，下一步挪出 `plugins/`，只许调别的 Operation。
  - **领域**（`plugins`）：插件，整合某个领域（`fs`、`model`、`ui`…）。
  - **基建**（`infra`，`stdlib/infra/`）：Harness 外面给的能力，由装配配置建好、宿主管启停：
    - `llm`：模型后端（`Llm`：`complete(context)`，消息与工具用 pi-ai 的格式）。实现 `piLlm({ model })` 经 pi-ai 调，「provider/模型 id」建的时候就找、配错装配即失败；key 由 provider 从环境变量读。
    - `workspace`：工作区（`Volume`）。
    - `state`：持久状态（`Volume`），宿主切成互不相干的几块：内核的写前日志在 `journal/`；每个插件的存储在 `store/<包名>/`。
  - **存储的抽象 `Volume`**：按相对路径 `read` / `write`（整个替换，不留半截）/ `stat` / `list` / `mkdir` / `glob`，`sub(path)` 取一个子目录当作独立的一块；越不出去（`..`、绝对路径、指向外面的符号链接都拒绝），出错信息里只有相对路径。`open` / `close` 由宿主在启动前、关停最后调。`localPath` 是它在本地文件系统上的目录，没有就是纯远程的。实现现在只有 `localDir(root)`（本地目录，也适用于已挂好的 FUSE、NFS 目录）；换成 rclone+FUSE 时写一个实现，`open` 里起 `rclone mount` 等它挂好、`close` 里卸下，其余照本地目录、`localPath` 是挂载点；对象存储可以直接实现这些方法，没有 `localPath`。插件不用改。
  - **注入**：插件写 `plugin({ needs: ["llm"] }, (config, { llm }) => …)`，装载时只注入它声明的，装配没提供就装载失败。能声明的是 `llm`、`workspace`、`store`（持久状态里属于它的那一块，看不到别的插件的，也碰不到写前日志）。
  - **用到本地路径的**：写前日志要同步写、fsync，要求 `state` 有 `localPath`，没有就启动失败；`fs_grep` 要让 ripgrep 扫真实文件，工作区没有 `localPath` 时以拒绝返回，别的文件工具照常（以后的 bash 同理）。
  - **检查**：插件与内核在同一个进程里挡不住 `import`，所以 `app/mvp/layers.test.ts` 查 app 的插件：不许 import `fs`、`child_process`、`net`、`http` 等，不许在运行时 import 模型 SDK（`import type` 可以），不许 `fetch`、读 `process.env`、用 `Bun.file` / `Bun.spawn` 之类。
- **原因**：换基建（本地目录换成挂载的远程存储、换模型供应商、换凭据的来处）只改装配配置；插件拿得到什么一目了然，权限就是 stdlib 给的加上装配注入的；凭据与供应商只在基建层。方案的服务按名字解析、按消费方创建，这里先只有宿主提供的这几种，插件之间还不互相提供服务。
- **影响**：
  - 写前日志的持久性取决于 `state` 的实现：本地盘照 fsync；rclone+FUSE 的写先落本地缓存再上传，进程或沙箱没了时缓存里还没传的会丢——写前日志宜放在真正持久的本地盘或持久卷上。
  - Unix socket 也要在本地文件系统上：`state` 换成挂载的远程存储时，socket 另放。
  - `stdlib` 的入口只导出基建的类型；实现按路径 import（`stdlib/infra/volume`、`stdlib/infra/llm`），免得每个插件 import `stdlib` 都带上模型 SDK。
- **代码**：`stdlib/infra/`（`index.ts` 的 `grant`、`journalDir`，`volume.ts`，`llm.ts`）、`plugin.ts`（plugin 的 needs）、`loader.ts`、`host.ts`；`app/mvp/main.ts`、`app/mvp/plugins/fs/operations.ts`、`app/mvp/layers.test.ts`。测试 `stdlib/infra/*.test.ts`。

| `attempt` | 恢复时重新执行的 Run（包括根）在上次的基础上加一，先记一行 `retry`，再崩一次还能接着加；`run.started` 在大于 1 时带上它 | `kernel.ts`（resume） |
| 不确定的值 | 经 Operation 取（`time_now`；以后 random、uuid），不直接用 `Date.now()`：结果随调用记进日志，重放时回送当初的值。调用结果要能 JSON 序列化 | `stdlib/plugins/time/index.ts` |
| 关停的两种模式 | `stop(timeoutMs)` 优雅关停：不接新的外部调用，树里新发起的调用与 park 停在边界上（不执行、不记日志）；等正在执行的调用跑完，没有正在执行的了（只剩停住的与 park）就把在途的树按 shutdown 杀掉，到超时则转强杀。`stop(0)` 强杀，什么也不等。日志都保留：优雅关停停在干净的边界上，重启后没有执行到一半的调用；强杀等同崩溃，在途的重新执行、attempt 加一。方案是「等在途的树收敛或超时」，树要跑很多轮或在等 park 时几乎总会拖到超时 | `kernel.ts`（stop、hold、checkQuiet） |
| 内核的生命周期 | 装配中（`use`、`register`）→ 启动中（排先后、查装饰器引用、插件 `onStart`）→ 运行中（接受调用）→ 关停中。`use` 只能在 `boot` 之前；`boot` 只能一次；`stop` 要在 `boot` 之后，重复调用（比如优雅关停中又强杀）时插件的 `onStop` 只跑一次。启动失败停在启动中，不再接受调用；已 `onStart` 的插件不回滚。`register` / `registerDecorator` 是底层接口，不受阶段限制 | `kernel.ts`（use、boot、stop） |
| 能拦的挂点 | 按这个挂点排好的先后问（见一.12 的 `order`），第一个拦下的生效，后面的不再问；拒绝结果的 `by` 是拦下的插件的包名。必须同步（转换是同步的，等不了；要做 IO 的策略用装饰器），写成 async 类型检查报错，运行时返回 Promise 按拦下处理；抛异常也按拦下处理（管控出错必须中断）并记下。在提交阶段之前：被拦下的结果照常进事件与日志（子调用是 `call.rejected`，退出是 `run.exited`，park 是没有 `park.opened` 的 `park.closed`，树是 `run.killed`），恢复重放时原样回送，不再问挂点；被拦下的外部调用与 `unpark` 只抛异常，什么也不记 | `plugin.ts`（BEFORE）、`kernel.ts`（before） |
| 通知类挂点的先后 | 一条事件先按它的 `after*` 挂点排好的先后调，再按 `afterAny` 排好的先后调 | `kernel.ts`（dispatch） |
| 装饰器引用的检查 | 启动时就查：默认装饰器与各 Operation 的自选装饰器都得注册了；插件的 Operation 引用别的包的装饰器（如 `fs_write` 用 `ui_approval`），那个包须在它的 `requires` 里。启动之后才注册的 Operation 仍在调用时查 | `kernel.ts`（checkDecorators、admit） |
| 挂点出错 | `after*`、`afterAny`、`afterStart` 不等它返回，出错（同步抛出或 async 拒绝）只记下，带上插件与方法名，不影响执行与其他插件；`onStart` 出错启动失败；`onStop` 出错只记下、继续关停 | `kernel.ts`（use、boot、stopPlugins）、`events.ts`（notify） |
| 插件的配置 | 装载器把配置原样交给工厂，缺省 `{}`，目前不校验；以后按插件声明的 schema 校验 | `loader.ts` |
| 入口的 `serve`（过渡） | 装载器把它从入口对象里拿出来交给宿主，其余部分照插件对象 `use`；宿主在 `boot` 之后调，装了入口时入口都结束服务即关停 | `loader.ts`、`host.ts` |
| 事件流的订阅者 | `kernel.events.subscribe` 留给测试与自己搭宿主的，与 `afterAny` 同语义；应用里打印事件、问人都由插件与入口用挂点做 | `events.ts` |
| `ctx.ops` 的运行时 | Proxy：`ctx.ops.包.键(入参)` 转成 `ctx.call("包_键", 入参)`；不认 `then`，免得 `await ctx.ops.fs` 之类把它当成 thenable。装饰器的 `ctx` 也有 | `ops.ts`（calls） |
| `ctx.park` 的约束 | 同一个 Run 同时只能 park 一次；Run 被杀后还在跑的代码调它抛异常；实现没等 park 就返回时，Run 等 park 关闭后才退出（与没 await 的子调用一样） | `kernel.ts`（park、settle） |

## 三、MVP 期间的临时做法

之后要回到方案，或另行决定。`stdlib/` 是框架包，放内核、宿主、入口与正式的插件；`app/mvp/` 下的插件（fs、model、agent、chat、trace）与装配配置只用来验证内核、演示怎么搭一个 harness，正式实现不用。

| 事项 | 方案 | 现在 |
|---|---|---|
| 装配配置 | 装配配置文件列出装哪些插件、各自的配置（6.1、附 A） | `app/mvp/main.ts` 只有一份装配配置交给宿主，按四层写（见一.16）：`infra` 里 `llm` 是 `piLlm({ model: MODEL })`（缺省 deepseek/deepseek-flash），`workspace` 是 `localDir(WORKSPACE_DIR)`（缺省 `./workspace`，启动时建好），`state` 是 `localDir(STATE_DIR)`（缺省 `./.harness`，在工作区之外：写前日志在 `journal/`，插件的存储在 `store/<包名>/`，chat 的对话历史在 `store/chat/conversation.json`）；`plugins` 按顺序列出插件；`serve.http` 的 Unix socket 是 `STATE_DIR/harness.sock`（路径有长度上限，约 100 字节，状态目录别放太深）；命令行参数 → 终端入口的第一句。API key（`DEEPSEEK_API_KEY`、`ANTHROPIC_API_KEY`）由 pi-ai 的 provider 从环境变量读。装配类型 `app/mvp/packages.ts` 手写，与装载列表一致。配置仍是 TS 代码，不是数据文件 |
| 公开表 | 外侧（script 包）只见公开表（7.2） | 分成两张（见一.15）：`public` 决定哪些 Operation 作为工具交给模型；`api` 表示能对外，实际对外的由装配配置的 `expose` 决定。MVP 对外 `chat_say`、`chat_reset`、`chat_greet`。script 包还没有 |
| 调模型 | model 插件经 `model-backend` 服务调后端（6.3、R17） | model 插件声明需要基建 `llm`（见一.16），经它调；`piLlm` 经 pi-ai（1.2）调，消息格式用 pi-ai 的。`model_complete` 的 `messages` 不做校验 |
| 文件工具 | fs 原语（附 A） | fs 插件包装 pi 的编码工具（`@earendil-works/pi-coding-agent`，钉在 1.2.0）：`fs_read`、`fs_write`、`fs_edit`（一次多处精确替换）、`fs_list`、`fs_find`、`fs_grep`，入参 schema 就是 pi 的 JSON Schema，结果是给模型看的文字。只引入它的工具模块：经 `tsconfig.json` 的别名 `pi-tools` 直接指到包里的 `dist/core/tools`，绕过包的导出表（整包引入要多约 0.5 秒、50 MB），所以版本钉死，升级时要核对。底层文件操作经 `operations.ts` 落到注入的工作区（`Volume`）上；交给 pi 的根是虚拟的 `/workspace`，入参里的路径先换成相对工作区的，模型看到的路径不带宿主机的目录。`fs_find` 用工作区的 glob，不用 fd；`fs_grep` 要工作区有本地路径、本机装有 ripgrep，不满足就以拒绝返回——都不让 pi 在运行时去网上下载二进制。pi 的 bash 还没接，要先做隔离（10.4） |
| fs 路径检查 | — | 两层：`fs_pathGuard` 在审批之前按字面拒掉越出工作区的路径（与 pi 解析路径的方式对齐：去掉开头的 `@`，`~` 开头的一律越界），越界的写不打扰人；真正的边界在工作区（`Volume`）的实现里：本地目录的实现对每个路径按字面查一次，再沿已存在的部分解开符号链接查一次，工作区里指向外面的符号链接也读写不到；出错信息里只有相对路径。`fs_grep` 交给 ripgrep 之前，pi 先经同样的检查确认要搜的路径在工作区里；ripgrep 不跟随符号链接 |
| agent 循环 | script 包 `agent.assist`，使用者可复制修改（3.3、R7） | 原生插件 `agent_assist`（`app/mvp/plugins/agent`）；script 运行时做好后挪过去 |
| agent 的入参与出参 | 入参 `history`，出参 `answer` 与更新后的 `history`（附 A） | 入参 `{ prompt, history? }`（这一句单独给，不用调用方拼进历史），出参 `{ answer, history }`；出参的 `history` 含这一轮的工具调用与结果，下一轮原样传回，交给模型的前缀逐字节不变。agent 不存状态，对话由调用方保存。每轮开头调 `model_compact` 检查一次，阈值是 agent 插件的配置 `compactOver`（缺省 60000） |
| 上下文压缩 | `model.compact`：入参 `history`、阈值 `over`，超过才压，产出新历史；只在轮次边界压，压缩后的历史交回调用方，同一段只压一次（8.3、R24） | `model_compact`：入参 `{ history, over, keep = 2 }`，出参 `{ history, compacted }`。大小按文字粗估（中日韩等宽字符一个算一个，其余四个字符算一个），不用模型回报的 usage：压缩后保留的旧回复还带着压缩前的用量，会让下一轮误以为还要压。按轮切（一轮从一条用户消息开始），保留最近 `keep` 轮，工具调用与结果不会被拆开；轮数不超过 `keep` 时原样返回。更早的部分写成纯文本记录（工具调用与结果都写成文字，结果超过 2000 字截断，免得要带工具定义）交给同一个模型写摘要；摘要并进保留部分的第一条用户消息，不另起一条，免得出现连续两条用户消息。它是原语，写摘要的那次模型调用直接经 pi-ai，不再建子 Run |
| 终端对话 | UI 渲染对话（3.5） | 终端入口 `stdlib/entries/console`：普通一行交给配置的 `say`（入参 `{ text }`），「/命令」调配置的命令（入参 `{}`），`/exit` 或输入结束不再服务；开场调 `greet`；返回的文字显示出来，失败显示 `失败（谁）：原因`。一份按行读的输入由对话与回答问题共用，排队读，不抢同一行；问题在开场之后才问。MVP 配成 `say: chat_say`、`/new` → `chat_reset`、`greet: chat_greet`，`bun start "第一句"` 从这句开始。对话由 chat 插件（`app/mvp/plugins/chat`）管：`chat_say` 依次调 `chat_load`、`agent_assist`、`chat_save`，历史存在 chat 自己的存储里（`STATE_DIR/store/chat/conversation.json`，整个替换），失败的一轮不存。存是 Run 里的子调用，存完根 Run 才退出、日志才删，原来「日志先删、对话后写」的缺口没有了。同一时间只该有一轮，两轮同时会争同一份历史 |
| 停下与接着做 | 关停时投递插件 flush、编排方对账（9.2、9.4）；关掉沙箱再起来能接着答问题（P3 验收） | 宿主：Ctrl-C 优雅关停（服务接口先停止接新连接，等在途调用最多 10 秒），再按一次强杀，进度都留在日志里；进程被杀也一样。终端里等输入时 Ctrl-C 由 readline 收到，终端入口转给宿主；停下时还有一轮没做完，终端提示「已停下，进度已保存」。再运行 `bun start`，终端入口先开场，再接着做它发起的、没做完的那一轮，再回到对话；终端打印 `↻ 接着做` 与重新执行的 Run 的「第 N 次」，停着的问题用原 id 再问一次。在提示符空闲时 Ctrl-C 直接退出。不想接着做就删掉 `STATE_DIR/journal` |
| 观测 | 投递插件订阅事件、送往观测平台（9.2） | trace 插件（`app/mvp/plugins/trace`）用 `afterAny` 按 Run 树缩进打印到终端；各 Operation 的入参、出参怎么摘要写在它里面，形状对不上时退回截断的 JSON |
| 给人看的问题 | script 包 `agent-ui` 约定格式，UI 认得并渲染；选项带 label、value 与说明（3.5、附 A） | stdlib 的原生插件 `ui`（`stdlib/plugins/ui`，入口要认得它的格式，所以放在 stdlib）：公开的 `ui_ask` 给模型用。payload 为 `{ question, options? }`，选项只是字符串；回答为 `{ option?, text? }`：选中的选项，和/或补充说明（没选选项时就是回答本身）。终端入口一次问一个：序号或选项原文选择、后接补充说明，`/skip [原因]` 撤回，输入结束时全部撤回；不是这个格式的 payload 原样显示 |
| 审批 | `approval` 装饰器，自选（5.2），装配侧决定装不装（3.5） | `ui` 插件的 `ui_approval`：`fs_write` 声明使用它（在 `fs_pathGuard` 之内）。选 yes 才放行，带说明时结果改为 `{ result, userNote }`；选 no 或只写了说明都拒绝，有说明时原因带上说明且 `retryable: true`。`fs` 的 `requires` 写了 `ui`，`ui` 的写了 stdlib 的 `harness`，缺了启动失败 |
