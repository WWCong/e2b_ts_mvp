# 实现与方案的差异

对照 `harness-技术方案.md`（下称「方案」），记录实现里与方案不一致、或方案没写而实现自定的地方。方案本身暂不改；实现有变化时同步更新本文件。

---

## 一、已定的设计改动

### 1. 命名：`包名_键名`

- **方案**：Operation 名为 `包名.函数名`，如 `fs.read`（1.3、6.1、7.3、附 A）。
- **实现**：`包名_键名`，如 `fs_read`。键名是它在插件对象 `operations` / `decorators` 里的键（见 12）。包名只含小写字母、数字与 `-`；键名只含字母与数字；整名最长 64。名字里恰好一个 `_`，就是分隔符。装上插件（`kernel.use`）时校验包名与整名。
- **原因**：模型的工具名只接受字母、数字、`_` 与 `-`。这样 Operation 名原样就是工具名，事件、模型历史、日志里处处同名，便于追踪，也不需要任何转写。
- **代码**：`stdlib/kernel/names.ts`、`kernel.ts`（use、register）。

### 2. Operation 的声明：`op()` / `decorator()`，入参用 Zod

- **方案**：导出函数即 Operation，JSDoc 正文是 `usage`，标签写 `@public`、`@decorators`、`@only` 等；d.ts 与 JSON Schema 由同一个工具在构建期从 TS 类型生成（6.1、7.3、R4、R19）。
- **实现**：插件对象的 `operations` / `decorators` 里放 `op({ input, usage, public, decorators, only, exclude, impl })` 或 `decorator({ onError, fn })` 的声明（插件对象见 12）。入参是 Zod schema：TS 类型由它推出，运行时按它校验，交给模型的 JSON Schema 在注册时由 `z.toJSONSchema` 生成。
- **原因**：一处定义同时得到类型、schema 与校验；不需要构建步骤，也不用解析注释。
- **影响**：`usage` 从 JSDoc 挪到字段；以后 script 包要在 QuickJS 里带上 Zod，解析开销待实测。
- **代码**：`stdlib/kernel/plugin.ts`、`kernel.ts`（use）。

### 3. 当前 Run 经显式的 `ctx` 传递

- **方案**：用 AsyncLocalStorage 绑定当前 Run，Operation 恰好一个入参；插件之间 `import { read } from "fs"`，打包时换成按名字的调用（6.2、3.1、R4）。
- **实现**：`ctx` 作为第一个参数：实现是 `impl(ctx, input)`，装饰器是 `fn(ctx, run, next)`。调别的 Operation 写 `ctx.ops.fs.read(input)`，名字是变量时写 `ctx.call(name, input)`（类型见 14），返回结果对象（`{ ok, value }` 或拒绝），而不是值本身。
- **原因**：没有隐式上下文，插件可以传假 `ctx` 单测，也没有「上下文丢失」这条残余风险（方案 10.8、附 C）。
- **代码**：`stdlib/kernel/run.ts`（Ctx）、`kernel.ts`（execute）。

### 4. 装饰器 id 不自定义

- **方案**：`@decorator <id>` 声明注册名（5.2）。
- **实现**：装饰器 id 与 Operation 同一套命名，就是 `包名_键名`。
- **代码**：`stdlib/kernel/kernel.ts`（use）。

### 5. 取消用 `ctx.signal`，不设 `run.cancelling` 责任链

- **方案**：取消「走 `run.cancelling` 后转 killed」，由插件在生命周期责任链上收尾（5.1、附 A）。
- **实现**：每个 Run 带一个 AbortController，`ctx.signal` 在 Run 被杀（取消或关停）时 abort。原语把它传给 fetch、子进程等，IO 当场中止。没有 `run.cancelling`。
- **原因**：比责任链简单，是 JS 的惯用法；内核不用等插件收尾，取消不会被拖慢。
- **代码**：`stdlib/kernel/kernel.ts`（kill）、`run.ts`（Ctx.signal）。

### 6. 装饰器的 `ctx` 上没有 `tools()`

- **方案**：调用方是装饰器时，交给模型的工具缺省为空（8.1）。
- **实现**：更严格：装饰器的 `ctx` 类型是 `Omit<Ctx, "tools">`，装饰器里写 `ctx.tools()` 直接编译不过。
- **代码**：`stdlib/kernel/chain.ts`（DecoratorCtx）。

### 7. 交给模型的工具由调用方显式传入

- **方案**：`model.complete` 的 `tools` 缺省为调用方能力面里公开的 Operation，不含 `model` 包自身（8.1）。
- **实现**：调用方用 `ctx.tools()` 取得工具列表，再作为入参传给 `model_complete`；`model_complete` 本身不公开，所以不会出现在工具列表里。
- **原因**：`model_complete` 保持为纯原语，工具列表只是数据；调用方传常量列表，前缀更好控制。
- **代码**：`stdlib/kernel/kernel.ts`（toolsIn）、`app/mvp/plugins/model/index.ts`。

### 8. 放行不发事件

- **方案**：装饰器链每一环的处置都进事件流（3.7-4、9.1）。
- **实现**：链序记在 `run.started.chain` 里；放行不发事件，只有改写、拒绝、出错各发一条（`decorator.rewrote` / `decorator.rejected` / `decorator.failed`）。
- **原因**：少发大量「什么都没做」的事件；链序加上这三类事件，足以还原每一环做了什么。
- **代码**：`stdlib/kernel/chain.ts`。

### 9. `running` ↔ `waiting` 不发事件；能力面不写进事件

- **方案**：每个状态转换点都发事件（9.1）；复盘靠「Run 建立时的能力面」（9.6）。
- **实现**：父 Run 何时在等，可由子 Run 的 `run.started` / `run.exited` 推出，不单独发事件。能力面由 Operation 的声明静态决定，看 operation 名加产物版本即可还原，不在每个 `run.started` 里重复。

### 10. 内核不注册 Operation；park 的 Operation 在 stdlib 的 harness 插件里

- **方案**：`harness.park`、`harness.exec` 是内核提供的 Operation（3.5、附 A「`harness` 包」）；`harness.park` 是唯一不靠子 Run 而进入 `waiting` 的 Run（3.4）。
- **实现**：内核只提供机制：实现的 `ctx.park({ schema, payload })` 让当前 Run 转 `waiting`，对外接口 `unpark` / `withdraw` 送值或撤回。Operation 形式 `harness_park` 在 stdlib 自带的 harness 插件里（`stdlib/plugins/harness`），装配时按需装载。装饰器的 `ctx` 没有 `park()`：装饰器要挂起就 `ctx.call("harness_park", …)`，好让外层装饰器（如无人值守的短路）看得到。
- **原因**：注册表里的 Operation 全部来自装载的插件，内核不带原语。
- **影响**：原生插件的实现可以直接 `ctx.park` 挂起自己的 Run，不经 park Operation，装饰器看不到这次挂起（原生插件本就是受信的内侧代码）。
- **代码**：`stdlib/kernel/kernel.ts`（park、unpark、withdraw）、`run.ts`（Ctx.park）、`chain.ts`（DecoratorCtx）、`stdlib/plugins/harness/index.ts`。

### 11. 恢复靠写前日志，没结束的树都能恢复

- **方案**：树空闲时写快照、活跃前删，只恢复空闲的树；任意步续跑交给工作流引擎（3.6、11.4、R11、R29）；装配配置 `snapshotDir`。
- **实现**：每棵树一个只追加的日志，放在内核专属目录（装配配置 `journalDir`）。日志是事件流的持久投影：每条事件先过提交阶段，由它推出日志行同步落盘，再交给订阅者与插件，内核才往下走；插件看不到这一步，也拦不了。调用发起、调用完成、park 关闭，都这样先落盘再继续；树结束或被取消时删，关停时保留。启动（`kernel.boot()`）时重建所有没结束的树：已完成的调用回放；崩溃时正在执行的 Run 用原 runId 重新执行，并经 `ctx.attempt` 告诉它这是第几次执行。要落日志、要恢复的东西一律经 Operation 取：时间这类不确定的值调 `time_now`，状态将来是 state 插件的 Operation（存储由插件自己管）；调用结果本就记进日志、重放时回送，内核不另设接口。
- **原因**：崩溃时正在执行的原语（比如发邮件）有没有生效，只有它自己知道。内核给出信号和稳定的 runId（可当幂等键），由原语决定查重、跳过还是重做，与 Temporal 的 attempt、Stripe 的 Idempotency-Key 同理。
- **影响**：每次调用多两次同步写盘；写原语要考虑 `attempt > 1`，不处理时语义是「至少执行一次」；日志随树增长，长期存在的树以后要压缩。内核仍不做重试策略与补偿。
- **代码**：`stdlib/kernel/journal.ts`（commit）、`events.ts`（EventStream 的提交阶段）、`kernel.ts`（recover、callChild、park）。

### 12. 插件是工厂函数；生命周期与事件挂点是插件对象上的方法

- **方案**：插件包导出函数即 Operation，`setup(config)` 拿配置（6.1、附 A）；插件经 `@on` 处理器订阅事件；启动、关停各有 `harness.started`、`harness.stopping` 责任链（9.2）。
- **实现**：插件包默认导出 `plugin((config) => 插件对象)`。装载时以装配配置调一次工厂，工厂里的变量就是这个插件实例自己的状态（一个内核一份），工厂本身也就是 `setup(config)`。插件对象里放：
  - `operations`、`decorators`：声明（见 2），名字取 `包名_键名`；
  - `onStart()`：启动时（`kernel.boot()`）按装载顺序逐个 await，抛异常则启动失败；之后才恢复没结束的树、开始接受调用；
  - `afterStart()`：启动完成后（树已恢复）通知；
  - `onStop()`：关停时，在途的树杀掉之后，按装载的逆序逐个 await（后装的可能依赖先装的）；
  - `after*(event)`：每种事件恰好对应一个方法（`afterRunStart`、`afterRunExit`、`afterRunKill`、`afterCallReject`、`afterParkOpen`、`afterParkClose`、`afterTreeRecover`，三种装饰器事件合为 `afterDecorate`），只读通知；
  - `afterAny(event)`：所有事件，投递、观测类插件用；
  - `before*(event)`：能拦的挂点，转换发生之前同步调，拿到将要发出的事件，返回 `{ veto: 原因 }` 即拦下：`beforeRunStart`（子调用以拒绝返回、不建子 Run；外部调用抛异常）、`beforeRunExit`（结果换成拒绝）、`beforeParkOpen`（不等待，park 直接以拒绝关闭）、`beforeParkClose`（外部送值或撤回抛异常，park 照旧等待）、`beforeTreeRecover`（这棵树不恢复）。

  没实现的方法不调。插件对象里有不认得的键（比如挂点方法名拼错）时装载即报错。
- **原因**：游戏引擎式的脚本挂点：插件想接哪个时机就实现哪个方法，一个对象就是插件的全部；工厂给每个内核实例一份独立的状态，配置不再走全局的环境变量。装饰器保留：它在 Run 里面、可回放、包住一次调用（审批的 park、计时、预算的预留与结算）、按 Operation 自选并有顺序；挂点是 Run 外面的全局时机。
- **影响**：方案 R14 要求全局行为由装配侧决定，插件不能因为注册了什么就改变全局行为。`before*` 能拦所有调用，是全局的；这里由装配侧决定装不装这个插件来体现。只有原生插件有挂点，script 包没有。
- **代码**：`stdlib/kernel/plugin.ts`（plugin、AFTER、BEFORE、PluginObject）、`kernel.ts`（use、boot、stop、before）、`loader.ts`。

### 13. 代码组织：`stdlib` 框架包与 `app`

- **方案**：插件与 script 包从 `harness` 包 import 运行时函数（`call`、`emit`、`spawn`）与内核的 Operation（`harness.park`、`harness.exec`）（3.1、附 A「`harness` 包」）；别的包 `import { read } from "fs"`。
- **实现**：
  - `stdlib/` 是框架包，import 名就是 `stdlib`（`tsconfig.json` 的 `paths`，Bun 运行时同样认）。`stdlib/index.ts` 是唯一的公开入口：写插件用的 `op` / `decorator` / `plugin` 与 `Ctx`、`Result` 等类型，搭应用用的 `Kernel`、`loadPlugin`。内核在 `stdlib/kernel/` 下，其余模块（日志、回放等）不导出。
  - stdlib 自带的插件在 `stdlib/plugins/` 下，按领域分包：`harness`（`harness_park`，即方案的 `harness.park`；以后放 `harness_exec`）、`time`（`time_now`）。应用按路径装载，如 `loadPlugin(kernel, "stdlib/plugins/time")`。
  - `app/` 下是用 stdlib 搭出来的 harness 实现，各自带入口与自己的插件；`app/mvp` 演示怎么搭。
  - 每个应用一份 `tsconfig.json`（继承根配置），只编译这个应用，它的装配类型不影响 stdlib 与别的应用（见 14）。
  - 运行时函数在 `ctx` 上（见 3），不从包里 import。
- **原因**：框架与应用分开，应用怎么搭一目了然；import 不再写一串 `../`。
- **代码**：`stdlib/index.ts`、`tsconfig.json`、`stdlib/plugins/`、`app/mvp/main.ts`。

### 14. 调用的类型从插件源码推出，由应用登记

- **方案**：包的 d.ts 由同一个工具在构建期从 TS 类型生成（7.3、R19）；插件之间 `import { read } from "fs"`，打包时换成按名字的调用（3.1、6.2）。
- **实现**：
  - `op()` 记下入参的类型（`z.input`，即调用方要填的形状，带默认值的字段可不填）与出参的类型（实现的返回值），`plugin()` 记下插件对象的具体类型。
  - 应用写一个装配类型文件（`app/mvp/packages.ts`），用 `import type` 把装了的包登记进 `Packages`（`declare module "stdlib"`）。不手写 d.ts，运行时什么也不加载。
  - 插件里写 `ctx.ops.fs.read({ path })`：包或 Operation 不在注册表里、入参不对，编译即报错；结果带类型，编辑器能补全。
  - `ctx.call(name, input)`：名字在注册表里时同样带类型；名字是变量（模型挑的工具）或不在注册表里（测试里临时注册的）时，入参与结果是 `unknown`，不报错。
  - 运行时 `ctx.ops.fs.read(x)` 就是 `ctx.call("fs_read", x)`，照常过装饰器、能力面、日志与事件，事件与日志里的名字不变。
- **原因**：类型与实现同源，不会对不上；不需要构建步骤；显式 `ctx` 下也能像调包里的函数一样读写。
- **影响**：
  - 类型只是契约：不知道能力面，也不知道这次装没装，这两样仍由运行时拒绝。
  - 装饰器改写的结果不反映在类型上（如 `ui_approval` 带说明时把结果包成 `{ result, userNote }`）。
  - 插件的出参若由调用自己包里 Operation 的结果推出，类型会绕成环，要给 `impl` 标返回类型。
  - `ctx.call` 不补全名字、拼错不报错：它只查名字里的那个包，查全表会把调用方自己的包卷进来、绕成环。写死的调用用 `ctx.ops`。
  - 装配类型文件要与入口装载的插件保持一致，以后由装配配置生成；给 script 包（QuickJS）的 d.ts 也可以从这份注册表生成。
- **代码**：`stdlib/kernel/ops.ts`、`plugin.ts`（op、plugin）、`run.ts`（Ctx、Result）、`app/mvp/packages.ts`、`app/mvp/tsconfig.json`；类型检查 `app/mvp/packages.check.ts`。

## 二、方案未规定、实现自定的

| 事项 | 实现 | 代码 |
|---|---|---|
| 调用结果的形状 | 成功 `{ ok: true, value }`；拒绝 `{ ok: false, by, reason, retryable }`，字段平铺 | `run.ts` |
| 实现抛异常 | 转成拒绝结果，`by` 为该 Operation 名，`retryable: false` | `kernel.ts`（invoke） |
| 入参不符合 schema | 建 Run 前以内核的拒绝返回，`retryable: true`（「这次没写对」）；实现拿到的是解析后的值（去掉多余字段、填上默认值） | `kernel.ts`（admit） |
| 建子 Run 前被拒的调用 | 目标不存在、不在能力面、超出保险丝、入参不符、发起方已结束，都不建子 Run，发 `call.rejected` | `kernel.ts`（callChild） |
| 对外 `start` 失败 | 还没启动完（`boot` 之前或启动中）、目标不存在、入参不符、超出保险丝、正在关停：直接抛错，不返回 runId | `kernel.ts`（start） |
| 资源保险丝缺省值 | 最大深度 32，同时存活的 Run 数 1024 | `kernel.ts` |
| 父 Run 何时退出 | 等它发起的子调用全部结束（包括没 await 的）才退出，不留悬空的子 Run | `kernel.ts`（settle） |
| 取消的范围 | 任何在途 Run 都能取消，连同其子孙；父拿到拒绝后照常往下执行。已结束或不存在返回 false | `kernel.ts`（cancel） |
| 被杀后仍在跑的代码 | JS 无法抢占：不理会 `ctx.signal` 的实现跑完但结果作废，之后它发起的调用被拒；还没走到实现的不再开始 | `kernel.ts` |
| `run.killed` 的原因 | `cancelled`（取消接口）或 `shutdown`（关停） | `events.ts` |
| 装饰器的 `next()` | 只能调一次，调第二次按该装饰器出错处理 | `chain.ts` |
| 配置冻结 | 走到实现时把 `run.input` 设为只读；目前只冻结 `input` | `run.ts`（freeze） |
| 公开的 Operation | 必须写 `usage`；入参转不成 JSON Schema（如 `z.date()`）的在注册时报错 | `kernel.ts`（register） |
| 工具列表的顺序 | 按名字排序，schema 按「调用方要填的形状」（`io: "input"`）生成 | `kernel.ts`（toolsIn） |
| park 等的值的 schema | JSON Schema：可序列化，能进事件；unpark 时用 `z.fromJSONSchema` 转成 Zod 校验。schema 本身不合法时 park 以拒绝返回，不进入等待 | `kernel.ts`（park） |
| 撤回的结果 | `{ ok: false, by: 挂起的 Operation（如 harness_park）, reason, retryable: false }` | `kernel.ts`（withdraw） |
| `park.closed` | unpark、撤回、取消时发，带这次 park 的产出 `result`。关停不发：park 没被回答也没被撤回，日志保留，恢复后按同一个 id 接着等 | `kernel.ts`（closePark、kill） |
| `unpark` / `withdraw` 失败 | id 不是等待中的 park，或值不符合 schema：抛错，park 照旧等待 | `kernel.ts` |
| 日志的内容 | 一棵树一个 JSON Lines 文件，以根 runId 命名。五种行：`root`（根与外部给的原始入参）、`call`（发起的调用：序号、目标、入参摘要、子 Run 的 runId）、`done`（第几个调用完成与结果，同一个 Run 的 done 行先后即完成顺序）、`park`（第几步的 park 关闭时的产出）、`retry`（恢复时重新执行了哪个 Run、第几次）。一个 Run 的调用与 park 共用一套序号，实现与装饰器的也一起编号；在内核就被拒的调用也记。每行都由事件推出：`run.started` → 根的 `root` 行、子 Run 的父的 `call` 行、重新执行的 `retry` 行；`call.rejected` → `call` 与 `done` 行；`run.exited` / `run.killed` → 父的 `done` 行；`park.closed` → `park` 行 | `journal.ts`（commit） |
| 写入 | 在提交阶段同步写并 fsync，落盘后事件才交给订阅者与插件、内核才往下走：调用落盘后才执行，结果落盘后才交给父，park 的值落盘后才送进去。子 Run 的入参不记：恢复时父会再发起同样的调用 | `events.ts`（emit）、`journal.ts`（commit） |
| 写盘失败 | 提交阶段抛的异常从转换点往外抛，这次转换做到一半；按崩溃处理：进程应退出，重启后从已落盘的部分恢复。后续：明确的 fail-stop | `events.ts`（emit） |
| 何时删、何时不记 | 按根的 `run.exited` / `run.killed` 处置：正常结束、被取消时删；关停保留；别的原因（比对不上、恢复时根建不起来）移到 `diverged/` 下留着排查，不再恢复。Run 已结束或被杀后它的事件不再记（日志只跟踪在途的 Run）：关停时日志停在被杀之前，重启后接着跑 | `journal.ts`（commit、end） |
| 恢复的入口 | `kernel.boot()`：插件都 `onStart` 过之后、`afterStart` 之前恢复，返回各树根的 runId 供收割。`start` 必须在 `boot` 之后，否则 `boot` 之前起的树会在恢复时再执行一遍。崩溃时写了一半的末行截掉。根都建不起来（Operation 没了、入参不再合法）时恢复失败 | `kernel.ts`（boot、recover）、`journal.ts`（readAll、fold） |
| 重放 | 重新执行的 Run 按序号回放：调用比对目标与入参摘要，已完成的回送记下的结果（不执行、不过链、不发事件），在途的子 Run 用原 runId 重新执行；park 已关闭的直接拿产出，没关闭的用原 id 重新开出（照常发 `park.opened`）。越过记录末尾后照常执行 | `kernel.ts`（callChild、park） |
| 回送的顺序 | 已完成的结果按崩溃前的完成顺序（同一个 Run 的 done 行与 park 行的先后）逐个交还，每交还一个先让代码跑一步，并发发出的调用拿到结果的先后与原来一致。在途重新执行的与越过末尾的新调用不参与排序 | `replay.ts` |
| 比对不上 | 只看代码看过结果的那些步：已完成的那一步对不上（目标、入参不同，或调用与 park 互换），或 Run 结束时还有已完成的记录没走到（`got exit`），判为对不上。整棵树按 killed 处理，原因写明哪一步（`diverged at #序号 of Operation: journal has …, got …`），park 作废，日志移到 `diverged/` | `kernel.ts`（diverge、callChild、park、settle） |
| 产物摘要 | Operation 与装饰器的声明及代码（impl / fn 的源码文本）、默认装饰器集，取 sha256，写进日志的根行。方案是「不一致不恢复」；实现只在 `tree.recovered` 里提示（`artifactChanged`），照常恢复，靠逐个调用比对兜底，升级代码时停在 park 上的任务不至于全部作废 | `kernel.ts`（artifact） |
| 恢复事件 | 每棵恢复的树发一条 `tree.recovered`：日志里已完成的调用与 park（带结果，重放时不再发事件，崩溃前没来得及发的 `run.exited` / `park.closed` 据此补齐）、要重新执行的 Run、产物是否变了。根建不起来时再发 `run.killed`，原因即收割到的拒绝原因；比对不上的同样是 `run.killed`（diverged …） | `kernel.ts`（recover）、`events.ts` |
| 事件的启动 id | 每条事件带 `boot`（UUIDv7，按时间有序），重启后 `seq` 从头数，下游按「boot + seq」排序。启动不发事件：换了 boot 即重启过，插件经 `onStart` / `afterStart` 得知 | `events.ts` |
| 事件里给日志用的字段 | `step`：`run.started` 是它在父里的第几步，`call.rejected` 是发起方的第几步，`park.closed` 是这个 Run 的第几步，即日志行的 `seq`，事件与日志一一对上（原名 `callSeq`）。`run.started` 的 `input` 是调用方给的原样入参（实现拿到的是按 schema 解析后的），日志的入参摘要与恢复时的比对都用它；根 Run 的 `run.started` 带 `artifact`（产物摘要） | `events.ts`、`kernel.ts`（execute、callChild、closePark） |
| 在途的那一步换路 | 崩溃时在途的那一步，结果从没交给过代码：重新执行时改发别的调用或改成 park（比如 `attempt > 1` 时先查重）不算对不上。旧的在途调用作废、不再执行，新调用照常执行并记一行覆盖旧的；没走到的只剩在途的，也作废 | `kernel.ts`（callChild、park） |
| `attempt` | 恢复时重新执行的 Run（包括根）在上次的基础上加一，先记一行 `retry`，再崩一次还能接着加；`run.started` 在大于 1 时带上它 | `kernel.ts`（resume） |
| 不确定的值 | 经 Operation 取（`time_now`；以后 random、uuid），不直接用 `Date.now()`：结果随调用记进日志，重放时回送当初的值。调用结果要能 JSON 序列化 | `stdlib/plugins/time/index.ts` |
| 关停的两种模式 | `stop(timeoutMs)` 优雅关停：不接新的外部调用，树里新发起的调用与 park 停在边界上（不执行、不记日志）；等正在执行的调用跑完，没有正在执行的了（只剩停住的与 park）就把在途的树按 shutdown 杀掉，到超时则转强杀。`stop(0)` 强杀，什么也不等。日志都保留：优雅关停停在干净的边界上，重启后没有执行到一半的调用；强杀等同崩溃，在途的重新执行、attempt 加一。方案是「等在途的树收敛或超时」，树要跑很多轮或在等 park 时几乎总会拖到超时 | `kernel.ts`（stop、hold、checkQuiet） |
| 内核的生命周期 | 装配中（`use`、`register`）→ 启动中（插件 `onStart`）→ 运行中（接受调用）→ 关停中。`use` 只能在 `boot` 之前；`boot` 只能一次；`stop` 要在 `boot` 之后，重复调用（比如优雅关停中又强杀）时插件的 `onStop` 只跑一次。启动失败停在启动中，不再接受调用；已 `onStart` 的插件不回滚。`register` / `registerDecorator` 是底层接口，不受阶段限制 | `kernel.ts`（use、boot、stop） |
| 能拦的挂点 | 按装载顺序问，第一个拦下的生效，后面的不再问；拒绝结果的 `by` 是拦下的插件的包名。必须同步（转换是同步的，等不了；要做 IO 的策略用装饰器），写成 async 类型检查报错，运行时返回 Promise 按拦下处理；抛异常也按拦下处理（管控出错必须中断）并记下。在提交阶段之前：被拦下的结果照常进事件与日志（子调用是 `call.rejected`，退出是 `run.exited`，park 是没有 `park.opened` 的 `park.closed`，树是 `run.killed`），恢复重放时原样回送，不再问挂点；被拦下的外部调用与 `unpark` 只抛异常，什么也不记 | `plugin.ts`（BEFORE）、`kernel.ts`（before） |
| 挂点出错 | `after*`、`afterAny`、`afterStart` 不等它返回，出错（同步抛出或 async 拒绝）只记下，带上插件与方法名，不影响执行与其他插件；`onStart` 出错启动失败；`onStop` 出错只记下、继续关停 | `kernel.ts`（use、boot、stopPlugins）、`events.ts`（notify） |
| 插件的配置 | 装载器把配置原样交给工厂，缺省 `{}`，目前不校验；以后按插件声明的 schema 校验 | `loader.ts` |
| 事件流的订阅者 | `kernel.events.subscribe` 保留给入口程序（终端打印、问人），与 `afterAny` 同语义 | `events.ts` |
| `ctx.ops` 的运行时 | Proxy：`ctx.ops.包.键(入参)` 转成 `ctx.call("包_键", 入参)`；不认 `then`，免得 `await ctx.ops.fs` 之类把它当成 thenable。装饰器的 `ctx` 也有 | `ops.ts`（calls） |
| `ctx.park` 的约束 | 同一个 Run 同时只能 park 一次；Run 被杀后还在跑的代码调它抛异常；实现没等 park 就返回时，Run 等 park 关闭后才退出（与没 await 的子调用一样） | `kernel.ts`（park、settle） |

## 三、MVP 期间的临时做法

之后要回到方案，或另行决定。`stdlib/` 是框架包，放内核与正式的插件；`app/mvp/` 下的插件（fs、model、ui、agent）与入口只用来验证内核、演示怎么搭一个 harness，正式实现不用。

| 事项 | 方案 | 现在 |
|---|---|---|
| 装配配置 | 装配配置文件列出装哪些插件、各自的配置（6.1、附 A） | 入口程序 `app/mvp/main.ts` 写死插件列表，把环境变量转成插件配置：`WORKSPACE_DIR` → fs 的 `workspace`（启动时建好），`MODEL` → model 的 `model`（装载时就找模型，配错即失败）。API key（`DEEPSEEK_API_KEY`、`ANTHROPIC_API_KEY`）仍由 pi-ai 的 provider 从环境变量读。装配类型 `app/mvp/packages.ts` 手写，与装载列表一致 |
| 公开表 | 外侧（script 包）只见公开表（7.2） | 还没有外侧；`public` 目前只决定哪些 Operation 会作为工具交给模型 |
| 调模型 | model 插件经 `model-backend` 服务调后端（6.3、R17） | model 插件直接依赖 pi-ai；`model_complete` 的 `messages` 不做校验 |
| fs 路径检查 | — | `fs_pathGuard` 只按字面判断，不跟随符号链接；报错会带出宿主机上的绝对路径 |
| agent 循环 | script 包 `agent.assist`，使用者可复制修改（3.3、R7） | 原生插件 `agent_assist`（`app/mvp/plugins/agent`）；script 运行时做好后挪过去 |
| agent 的入参与出参 | 入参 `history`，出参 `answer` 与更新后的 `history`（附 A） | 入参 `prompt`，出参 `answer`，单轮任务；多轮对话与 `model.compact` 以后再加 |
| 观测 | 投递插件订阅事件、送往观测平台（9.2） | 入口程序 `app/mvp/main.ts` 订阅事件流，由 `app/mvp/trace.ts` 按 Run 树缩进打印到终端 |
| 给人看的问题 | script 包 `agent-ui` 约定格式，UI 认得并渲染；选项带 label、value 与说明（3.5、附 A） | 原生插件 `ui`（`app/mvp/plugins/ui`）：公开的 `ui_ask` 给模型用。payload 为 `{ question, options? }`，选项只是字符串；回答为 `{ option?, text? }`：选中的选项，和/或补充说明（没选选项时就是回答本身）。入口程序由 `app/mvp/prompt.ts` 在终端里一次问一个：序号或选项原文选择、后接补充说明，`/skip [原因]` 撤回，输入结束时全部撤回 |
| 审批 | `approval` 装饰器，自选（5.2），装配侧决定装不装（3.5） | `ui` 插件的 `ui_approval`：`fs_write` 声明使用它（在 `fs_pathGuard` 之内）。选 yes 才放行，带说明时结果改为 `{ result, userNote }`；选 no 或只写了说明都拒绝，有说明时原因带上说明且 `retryable: true`。装 `fs` 就得装 `ui` 与 stdlib 的 `harness` |
